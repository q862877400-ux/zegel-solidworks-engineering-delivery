# 分系统开发总纲

版本 v0.1 · 2026-11-04 · 本文只定**原则、边界与判据**，不定施工顺序

---

## 一句话

> **把 AI 之前就存在的「代码 → 零件」生成器，重整成一层分系统方法：**
> **输入是需求，输出是「参数表 + 溯源 + 未覆盖清单」，几何藏在下面，AI 只在上面翻译。**

---

## 一、背景

### 1.1 外部：正在发生的一场重复发明

2024 年起，「text-to-CAD」被当成新事物重新包装。但它不是新的：

| 年 | 已经有人做过 |
|---|---|
| 1988 | Pro/ENGINEER 的 **Pro/PROGRAM**——模型里嵌一段程序，读外部 txt 就重建整套装配 |
| 2010 | **OpenSCAD**——文本即模型 |
| 1998 | **GearTrax**——十几个参数出一对真渐开线齿轮 |
| 1985 | **KISSsoft**——按 ISO 6336 算齿轮强度 |

这些工具沉淀下来的是**公式、参数表与校核规则**——不是代码风格，是可以直接拿来用的工程资产。

**三条已经核实过的事实**，决定了我们不能照抄它们，也不能无视它们：

1. **SolidWorks Toolbox 的齿轮不是真渐开线。** 官方帮助页原文：*"They are not true involute gears that you can use for manufacturing."* 所以它连"精度几级"都无从谈起。
2. **GearTrax 一族不做强度校核。** 两份官方 PDF 全文检索 `strength` / `6336` / `AGMA 2101` / `ISO 1328`，**0 命中**。它做的是齿形，强度要另找 KISSsoft 或外接 FEA。
3. **STEP 导入会杀死参数化。** 导进来是哑实体：没有特征树、没有约束、没有参数，改一个齿数要重新导一次。**要可交付的工程模型，只能在 SolidWorks 里重建。**

（证据见同目录 `00-报告.md` / `01-常用件复用清单与架构.md`）

### 1.2 内部：我们自己已经付过一次学费

- `capabilities.yaml` 里**组件生成器 = 0 个**。
- 我们**自己写过一次齿轮**：`archive/inherited-methods/scripts/sw_gear.py`，20.6 KB、4 个公开函数、`SpurGearSpec` → `calculate_external_spur_gear` → `evidence()`。
- 它的 level 至今是 **`stitched`**，`mcp_tools: []`，归档理由原文：**「齿轮属【方法】不属【工具】」**。
- 它自己写的 limitations 很诚实：仅标准全齿高外啮合直齿；齿根是径向过渡 + 圆弧，**不是滚刀 trochoid**；齿廓弦线离散；不含斜齿/内齿/齿条/变位/侧隙/修形/公差/材料/强度。

**结论**：手搓几何这条路我们走过，走到 `stitched` 就停了。**再做第二个 `sw_gear.py` 没有意义——要做的是承载 `sw_gear.py` 这类东西的那一层。**

### 1.3 由此得到的一句话判断

> 我们缺的不是「一个齿轮生成器」，是**一层统一的、每个零件族都照着填的方法层**。

## 二、目的

### 2.1 三句话

1. **让用户说人话就能出零件参数**——不必懂「模数」「重合度」「配合代号」。
2. **让输出的每个参数都能被追问来源**——算的、选的、查的、锁的、还是我替他定的。
3. **让专业用户能接手打磨**——拿到的是草案与工作台，不是黑箱成品。

### 2.2 交付物形态（三者缺一不可）

| 交付物 | 形态 | 给谁看 |
|---|---|---|
| **方法模块** | Python，纯计算，可单测，不碰 COM | 代码 / CI |
| **参数溯源表** | 每行：参数 · 含义 · 值 · 来源 · 依据 · 怎么改 | 工程师 / 客户 |
| **未覆盖清单** | 明确写出"我没算什么" | 审核 / 交付 |

### 2.3 非目标（明确不做）

1. **不做装配级推理**（行星、多级、箱体）——那是下一层，本总纲不覆盖。
2. **不做自然语言理解**——AI 在上一层，本层只吃结构化的需求对象。
3. **不做几何重写**——能复用就复用，复用的许可证要标清。
4. **不替换 SolidWorks 的建模能力**——只决定"建什么"，不决定"怎么点鼠标"。
5. **不追求族数**——先做通一个族再谈覆盖。
6. **不承诺强度**——除非该族真的把强度接进来了（见 I3）。

## 三、五条基本判断

这五条是这份总纲的骨头。任何方案与它们冲突，改方案，不改它们。

### J1 复用数学，不复用文件
公式与参数表可以移植（数学不受版权保护），**代码要按许可证处理**，**模型文件一律不用**（STEP 杀参数化）。
*反面案例*：直接 `export_step` 一个 CadQuery 齿轮导进 SolidWorks → 哑实体，不可编辑。

### J2 确定性内核 + AI 外壳
同一个需求永远得到同一套参数；**AI 只做翻译、组合、解释，不改几何代码**。
*反面案例*：让 AI 每次现写一段建模代码 → 每次都是新的未测代码。

### J3 参数图优先于参数表
先问「哪些参数该问人」，再问「怎么问」。**能推出来的不许问。**
*反面案例*：把 GearTrax 的二十几个输入框原样搬过来，只把标签翻译成中文。

### J4 溯源先于数值
一个数字对不对无法当场判断；**它从哪来，一定判断得了**。
*反面案例*：报告只给结果，不给依据——客户不敢用，工程师不敢信。

### J5 分系统先于装配
每个族先各自跑通、各自出表；装配是后面的事。
*反面案例*：一上来做行星轮系，结果每个齿轮的参数都还没定死。

## 四、硬原则（违反即返工）

| # | 原则 | 判据（怎么算违反） |
|---|---|---|
| **I1** | 几何内核只有一份，AI 不写它 | 出现"按需求生成一段几何代码"的路径 |
| **I2** | 每个参数必须有来源，六类之一：**问 / 算 / 选 / 查 / 锁 / 假设** | 表里出现无来源的值，或来源写"系统默认" |
| **I3** | 未覆盖项必须随产物输出 | 出了参数表却没有"C. 我没算什么" |
| **I4** | 判据必须显式：写清口径与出处 | 同一个量在两处取不同值而不声明（如 z_min 17 vs 18） |
| **I5** | 带量纲的形参，名字里必须有单位后缀 | `module` 而不是 `module_mm` |
| **I6** | 参数域封闭且显式；越界**报错**，不凑合 | 给一个"差不多能用"的结果代替拒绝 |
| **I7** | 复用要标来源与许可证；GPL/AGPL 只读思想 | 把 GPL 代码抄进 `scripts/` |
| **I8** | 分系统只交接口，不交装配 | 方法模块里出现"装到哪个面" |

**I1–I8 全部可 grep 或可单测**——这是它们能当原则而不是口号的前提。

## 五、分层与接口（概念层，不是实现顺序）

```
┌──────────────────────────────────────────────┐
│ AI 层：意图 → 需求对象 · 措辞降级 · 失败解释     │  ← 可换、可变、不保证确定性
├──────────────────────────────────────────────┤
│ 分系统方法层（本总纲的范围）                   │  ← 确定性、可单测、纯计算
│   需求对象 → 参数图推导 → 校核 → 参数集        │
│              ↓                                │
│           溯源表 + 未覆盖清单                  │
├──────────────────────────────────────────────┤
│ 几何层：SolidWorks API（项目已有）             │  ← 按参数集建模
└──────────────────────────────────────────────┘
```

**接口契约（每个族必须实现同一组）**：

| 成员 | 职责 |
|---|---|
| `Request` | 需求对象，2~3 个必答项 |
| `derive(request)` | 推导 + 校核，返回参数集 / 诊断 / 未覆盖 |
| `rows` | 溯源表数据（六来源） |
| `render()` | 人读输出（客户视图 / 工程师视图） |

**一个族做完的标志**：这四样齐全，且有契约测试。

## 六、与 SW 项目的关系

| 项 | 定位 |
|---|---|
| **形态** | **方法层**（`scripts/` 下的 Python 模块），**不进 MCP 工具表** |
| **依据** | 项目既定判断：「齿轮属【方法】不属【工具】」 |
| **对 AI 暴露** | 少量薄壳工具，一个入口覆盖多族 |
| **证据** | 沿用 `evidence()` 契约，把"几何证据"扩到"参数来源证据" |
| **门禁** | 落进 `scripts/` 时按项目流程走：`release_check` + 五统一 + `capabilities.yaml` |
| **level** | 几何侧未真机验证前，**一律 `stitched`，不许写 `verified`** |

## 七、成功判据

分系统这一层算不算成立，看三条，不看族数：

1. **一个非专业用户**，只用 2~3 句人话，能得到一份**他自己看得懂、且愿意拿去给人看**的参数表。
2. **一个机械工程师**，能在同一份表上**锁定任意参数**，其余自动重算，并知道改了会连带改什么。
3. **一份审核意见**，能指出表里哪一行缺依据——**说明这一行本来就有依据可指**。

三条里任意一条不成立，这一层就没做成。

## 九、变更规则

- **改原则（三、四节）**：必须说明"哪条现实证据推翻了它"，并把旧原则与推翻依据一并留档。
- **改范围（二节）**：可以，但要同步更新"非目标"。
- **改施工顺序**：**不属于本总纲范围**，随时可调，不必改本文件。
