# 参数图：不是把 40 个问题翻译成人话，是把 40 个问题压到 3 个

设计文档 · 2026-11-04 · 配套脚本 `proto/derive_gear.py`（输出 `demo_gear.txt`）

---

## 0. 结论

你说得对，但真正的杠杆不在你指的那一处。

- **把 40 个专业术语翻译成 40 句人话，客户还是被问 40 次。**
- **真正的解法是：这 40 个里，只有 2~3 个该问人，其余 37 个该由生成器自己推。**

一个生成器对外暴露几十个参数，**是设计失败，不是 UI 问题**。GearTrax 让你填二十多项，是因为它把自己定位成「**设计工具**」（给工程师做设计用），而不是「**需求 → 零件**」。

**我们要做的不是它的界面汉化版，是把它的参数表换成一张推导图。**

---

## 1. 参数图（不是参数表）

参数之间是**有向图**，不是一张平铺的清单：

```
【输入节点】用户可答，2~3 个
     i（减速几倍）      a（两轴能塞多宽）     用途（吵不吵 / 扛不扛）
        │                    │                      │
        └────────┬───────────┘                      │
                 ▼                                  ▼
【推导节点】生成器算，绝不该问           【校核节点】判据，不是参数
     z1, z2, m, d1, d2, b, da, df          εα ≥ 1.2 · z1 ≥ 17 · σH · σF
```

**三条硬规则：**

1. **推导节点不许问用户。** 问了就是把设计责任推回去。
2. **图里不许有环。** 「z1 由 a 定、a 又由 z1 定」这种，一出现就是死循环；必须指定谁是主输入。
3. **每个推导节点必须带一条依据**（公式 / 标准 / 表），否则它就是个魔数。

---

## 2. 最小必答集：每族 2~3 个

| 族 | 必答（客户能答） | 全部由生成器推导 |
|---|---|---|
| **齿轮副** | 传动比 i · 中心距 a（或外径上限） · 用途（安静/重载） | 模数 m、齿数 z1/z2、齿宽 b、齿顶/齿根圆、重合度、变位量 |
| **带传动** | 功率 · 主动转速 · 传动比 | 带型、带长、中心距、包角、根数 |
| **链传动** | 功率 · 转速 · 传动比 | 链号、齿数、链节数、中心距 |
| **弹簧** | 载荷 · 变形量（或刚度） · 安装空间 | 线径、中径、有效圈数、旋绕比、应力 |
| **轴** | 扭矩 · 支点跨距 · 有无冲击 | 轴径、台阶、键槽、疲劳安全系数 |
| **板件** | 载荷 · 跨度 · 「别软 / 别坏」 | 壁厚、加强筋、材料等级 |

**判据**：一个必答项 **必须是客户在 10 秒内能答、且答错也知道错在哪** 的。「中心距」能答（拿尺量），「重合度」不能答。

---

## 3. 锁定机制：工程师的接管口

推导图不是把工程师的手捆住。**任何推导节点都可以被 pin（锁定）成输入**：

```
默认：i + a  →  推导出 m=1.25, z1=20, z2=50
工程师：z1 锁定 20（我有现成刀具）  →  图绕过 z1 节点，其余照算
```

**三条配套规则：**

1. **pin 之后仍要过校核**——锁定不改判据，只改来源；
2. **过不了就说清是谁卡住**（见 §4 案例 4：给最近三个可行组合，不给一句"无解"）；
3. **pin 必须进 evidence**：「z1=20 由工程师指定，未按根切规则推导」。

> **灵活性来自「能锁哪个节点」，不来自「能填所有节点」。** 这两件事看起来像，实际上相反：前者让系统更强，后者让系统更脆。

---

## 4. 实测：2 个问题能不能出一个齿轮副

脚本 `proto/derive_gear.py`，只用精确几何关系（`a = m(z1+z2)/2`、`cos αa = z cos α/(z+2)`、`εα` 公式），**没有编造任何强度系数**。z_min=17 与模数系列取自本机 KB `直齿圆柱齿轮选型.md`。

| 案例 | 输入 | 输出 |
|---|---|---|
| **1 客户** | i=3、a=40 mm | m=1、z1=20、z2=60、d1=20、d2=60、b=10、**εα=1.67**、z1≥17 ✓ |
| **2 客户** | i=3、a=30 mm | **无解**，但说清：最小不根切组合 z1=17/z2=51 需要 **a=34 mm**；三条出路（放宽中心距 / 减小模数 / 用变位） |
| **3 工程师** | i=2.5、a=43 mm、**锁 z1=20** | m=1.25、z2=50、a=43.75、εα=1.66；锁定生效，其余照算 |
| **4 工程师** | i=2、a=80 mm、**锁 m=2** | 整数齿凑不上：最近是 **a=81（z1=27）差 +1 mm**、**a=78（z1=26）差 −2 mm**；给出三个候选而非一句"不行" |

**两个客户案例里，客户各只答了 2 个问题**（"减速几倍""两轴之间能塞多宽"），剩下 9 个参数全部由推导链给出。

**案例 2 才是重点**：失败时给出的不是「无解」，而是**「最小可行中心距 34 mm」+「三条具体出路」**。这就是「可靠」的样子——**它不会给你一个凑合的齿轮，它会告诉你差在哪、怎么补**。

---

## 5. 为什么这样才叫「又可靠又灵活」

| | 传统的几十参数表单 | 参数图 |
|---|---|---|
| 客户负担 | 40 个问题，第 3 个就烦 | 2~3 个可感知问题 |
| 工程师负担 | 40 个问题，能填但要填 | 2~3 个 + **想锁哪个锁哪个** |
| 出错方式 | 填错一个，全盘错且看不出 | 推导错=代码 bug，可测；参数不合=当场报 |
| 校核 | 事后检查（常常没做） | **推导链里就跑，出不来就没有模型** |
| 可追溯 | 「用户填的」 | 每个值有来源：用户答的 / 推导的 / 锁定的 |

**一句话**：把「填参数」变成「答需求」，把「四十个输入」变成「两三个输入 + 一张可锁的推导图」。

---

## 6. 与语义层的接合

- **每个输入节点挂一张语义卡**（`params.jsonl`，含 L4–L0 五级措辞）；
- **每个推导节点挂一条依据**（公式 / 标准条款 / 表）；
- **出结果时同时给三样**：客户视图、工程师视图、「我替你决定了什么」清单。

三件东西合起来是一条完整链路：

```
用户人话 →[语义卡/L0~L4]→ 输入节点 2~3 个
                              ↓
                        [参数图推导 + 校核]
                              ↓
              客户视图 / 工程师视图 / 假设清单
```

---

## 7. 必须承认的边界

**本 demo 只做了几何推导**（a、i、z、m、εα、b），**没有做强度校核**。

真正的齿轮设计还要：材料与热处理 → [σH]、[σF]；工况 → 载荷系数 K_A/K_V/K_α/K_β；再按接触/弯曲疲劳反算模数。**那部分必须按 KB 的完整公式与系数表接，不能拿本文的数字当设计结论。**

**本文证明的只有一件事**：*「2 个问题 → 一整套几何参数 + 一条可解释的失败路径」是可行的。*
