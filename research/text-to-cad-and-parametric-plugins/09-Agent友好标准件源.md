# 面向 Agent 的标准件源：机械行业还没有自己的 DigiKey

调研 2026-11-04 · 配套 `part_sources.jsonl`（13 个源，含 3 个电子行业标杆）

---

## 0. 结论

**机械行业没有一个「机械版 DigiKey API」**——自助注册、给个型号就返回可用模型的那种。电子行业有三个（DigiKey、SnapEDA、Ultra Librarian），机械一个都没有。

所以「嘉立创插件」这条路笨，不是因为选错了插件，是因为**你在用电子元件的生态解决机械标准件的问题**（嘉立创/立创商城是电子元件体系，LCSC）。

**但路是有的，而且有比插件好得多的形态：**

| 路线 | 代表 | 形态 | 现在能不能用 |
|---|---|---|---|
| **A. 命令行包管理** | **PartCAD** | `pc` 命令 + 公共仓库，参数化取件 | ✅ 能，**首选** |
| **B. 开源数据 + 后端** | **BOLTS** | 结构化数据 + FreeCAD/OpenSCAD 后端 | ✅ 能，但无 SW 后端 |
| **C. 厂商直下** | McMaster / MISUMI / SKF / Schaeffler | 网页/半接口，按型号取模型 | ✅ 能，需逐个接 |
| **D. 企业 API** | TraceParts / CADENAS | REST + apiKey | ⚠️ 要商务谈判 |
| **E. 自建索引** | 我们自己做 | SQLite + 直链 + 缓存 | ✅ 兜底，也最可控 |

---

## 1. 先定判据：什么叫「Agent 友好」

不是「有模型就算」，六条缺一不可：

| # | 判据 | 为什么 |
|---|---|---|
| 1 | **免登录，或一次 API key** | 每次要人工点登录 = 不可自动化 |
| 2 | **稳定标识**（标准号+规格 → 唯一件） | 否则每次都要"猜 URL" |
| 3 | **机器可读目录**（能枚举、能查询） | 否则无法"按需求找件" |
| 4 | **几何文件直链**（STEP/SLDPRT，一次 GET 落盘） | 否则要走浏览器点击 |
| 5 | **不依赖 JS 渲染** | 否则抓不到内容 |
| 6 | **ToS 允许自动化** | 否则不可持续 |

**一句话判据：能不能生成一条 `curl` 命令把模型拿下来。** 能，就是 Agent 友好；不能，就是给人用的。

## 3. 一条必须先澄清的事：**买件根本不需要特征树**

前面几份文档我反复说「STEP 导入会杀死参数化」。**那条针对的是"自己造的件"。**

买来的标准件不一样：

| | 自己造的件 | 买来的标准件 |
|---|---|---|
| 需要特征树吗 | **要**（要改、要参数化重建、要出图） | **不要**（尺寸由厂商定义，你永远不改它） |
| 需要什么 | 全约束草图 + 特征 + 可重建 | **外形准确 + 质量/体积对 + 能装配** |
| STEP 合适吗 | ❌ 杀死参数化 | ✅ **完全合适，甚至更好**（文件小、跨版本、无重建开销） |

**这条把架构解开了**：

> **造件走原生特征树；买件走 STEP / 简化体。**

之前那个矛盾是我把两类件混在一起说了，现在分开。

## 4. 推荐架构：四档 fallback

```
① 首选  PartCAD（命令行，可枚举，参数化）
          ↓ 找不到 / 无该件
② 厂商直下（McMaster 品号 / MISUMI 型号 / SKF·Schaeffler 牌号）
          ↓ 需要批量 / 商用
③ 企业 API（TraceParts / CADENAS，谈 apiKey）
          ↓ 都不行
④ 自建索引（SQLite + 直链 + 缓存 + 校验和）
```

**为什么 PartCAD 排第一**：它是唯一一个把零件当**软件包**的东西——

```
pc ide view //pub/std/metric/cqwarehouse:fastener/hexhead-din931
pc add -p size=M4-0.7 -p length=30 ...
```

**包路径 + 对象名 + 参数**，这就是 Agent 最舒服的寻址方式：可枚举、可拼、可缓存、可版本化。而且它底层直接复用 `cq_warehouse`（Apache-2.0）这类我们已经在用的库。

**局限**：它的覆盖以公制标准件与开源生态为主，**没有中国厂商的现货件号**，也**没有 SolidWorks 后端**（出 STEP 给我们导）。

## 5. 「自建索引」到底长什么样（针对"插件太笨"）

插件之所以笨，是因为**它把"取件"做成了一个 GUI 动作**。正确的做法是把它做成**一张表 + 一条 curl**：

| 字段 | 例 |
|---|---|
| 标准 | GB/T 5783 |
| 规格 | M6×20 |
| 厂商 | MISUMI |
| 件号 | HCB8-20 |
| 模型 URL | `https://…/part/HCB8-20.step` |
| 格式 | STEP |
| 许可/条款 | 厂商条款，仅内部设计用 |
| 抓取日期 | 2026-11-04 |
| 校验和 | sha256 |

**取件动作 = 一条 HTTP GET → 落盘 → 校验 sha256 → 导入 SolidWorks。**

判据还是那一句：**能生成一条 curl，就算 Agent 友好；只能点鼠标，就是给人用的。**

**这条路的成本主要在"建表"**，而建表可以半自动：`sw_misumi.py` 已经能免登录做**型号规范化 + 全文检索**，缺的是「型号 → 模型 URL」这一步的映射，那一步用一次人工标注 + 规则外推就能起步。

## 6. 电子行业已经做到了什么程度（对标，不是羡慕）

| 源 | 能力 |
|---|---|
| **DigiKey** | OAuth2（自助注册），Product Information V4：按 MPN/关键词/厂商/分类检索；沙箱与生产分离 |
| **SnapEDA / SnapMagic** | **给 MPN → 返回符号/封装/3D**，PCB 工具里自动解析 BOM |
| **Ultra Librarian** | 1600 万+ 元件，REST API，与主流 ECAD 集成 |

**这三家证明了一件事**：**「型号 → 可用 CAD」这个中间层在技术上完全可行、且可以做到千万级。**

机械侧缺的不是模型（TraceParts 有 400+ 厂商、3D ContentCentral 有百万件），缺的是**"自助、按型号、无谈判"的那一层**。所以我们的策略不该是等它出现，而是：**先把 PartCAD / 厂商直下 / 自建索引这三档搭起来，等哪个厂商开放 API 再接。**

## 7. 风险

| 风险 | 说明 |
|---|---|
| **ToS** | McMaster / SKF 等页面级源，**未明确允许批量自动化**，批量抓取前必须评估条款；TraceParts/CADENAS 走正式 API 就是为了绕开这个 |
| **模型质量** | 社区件（GrabCAD）与部分厂商件可能只有外形、无内部结构；**买件的判据是"外形 + 质量对"，不是"看着像"** |
| **版本漂移** | 厂商更新件号后旧链接可能失效 → **必须落盘 + 缓存 + 校验和**，不能每次现取 |
| **许可污染** | 厂商模型通常"仅用于设计"，不能转售或再分发 → 入库时记来源与条款 |
| **离线** | 断网时要有本地缓存层，不能设计流程依赖在线 |
