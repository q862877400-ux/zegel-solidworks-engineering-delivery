# 造环节开发计划

2026-11-04 · 配套 `proto/build_plan.py` + `proto/test_build_plan.py`（M0 已跑通，17 条测试）

---

## 0. 结论

「造」这一环不是「调 API 画图」，是**把几何变成一份可校验的计划，再交给一个很薄的执行器**。

三个事实决定了这个架构：

| 事实 | 出处 |
|---|---|
| **① 建模入口的单位口径有三套并存**，而且已经出过 **1000× 实物尺寸事故** | 归档 `sw_gear.py` 里的复盘注释 |
| **② 归档实现是折线弦近似**，默认一个齿轮就是 **700 条草图线段** | 本次实测 |
| **③ 大部分时候（CI / 开发机）没有 SolidWorks** | 项目事实 |

→ 所以流水线必须是：

```
Request ──derive()──► 参数集（纯数学，已有 v0）
               │
               ▼
         FeaturePlan  ← 纯数据：草图实体 + 特征 + 预期体积/包围盒
               │
               ▼
         execute()    ← 薄执行器，全项目**唯一**碰 COM 的地方
               │
               ▼
          verify()    ← L3 体积/包围盒比对，L4 三视图
```

---

## 1. 为什么 FeaturePlan 是「数据」而不是「调用序列」

| 理由 | 具体好处 |
|---|---|
| **可在无 SW 的机器上验证** | M0 的 17 条测试全部离线跑，0.07 s |
| **可换后端** | 同一份 plan 可以发 SW COM，也可以发 OCCT 出 STEP（买件用得上） |
| **可 diff / 可存档 / 可回放** | 出问题时能比「上次的 plan」和「这次的 plan」 |
| **单位转换只剩一个点** | 三套口径全压到 `to_meters()` 一处，改一次就够 |

**反面做法**：直接写 `sketch_line(...)` 一长串。这样任何一次单位错、任何一次 SW 版本差异，都要真机才能发现——而归档代码已经证明了这条路的代价：**一个 1000× 的 bug，只有真机量包围盒才能发现。**

---

## 2. 单位口径表（钉死，不许改）

| 接口 | 收什么单位 | 出处 |
|---|---|---|
| `sketch_line(x1,y1,x2,y2)` | **毫米** | 归档注释 + 1000× 事故复盘 |
| `sketch_circle(cx,cy,r)` | **毫米（半径）** | 同上（曾误传 `d/2000`） |
| `extrude_boss(depth)` | **米** | 官方 `D1` = meters |
| `outline_points_m` | **米** | 命名即为米 |

**规则**：
1. `FeaturePlan` 内部**一律毫米**；
2. **只有 `to_meters()` 一个函数**做转换；
3. 测试里有一条专门的断言：坐标必须落在毫米量级（>1 且 <1000），**防止再犯 1000×**。

## 3. M0 已经跑出来的东西

命令：`python build_plan.py`（在 `proto/` 下）

```
SpurGear_m1_z20｜单位=mm｜草图实体 700 个（线段 700 / 圆 0）
  拉伸 10 mm（送 SolidWorks 时转成 0.01 m）
  预期体积 3064.56 mm³｜预期包围盒 22.00 × 22.00 × 10.00 mm
  轮廓 700 点，形式=polyline_chord_approximation，多边形面积 306.46 mm²
```

**三个关键点**：

1. **预期体积能算出来**：`体积 = 轮廓多边形面积 × 齿宽 − 轴孔面积 × 齿宽`。建完直接比对——**验证被左移到了计划阶段**。
2. **物理约束能自查**：体积必须落在「齿根圆柱体积」与「齿顶圆柱体积」之间（测试里就这么断言的）。
3. **包围盒 = 齿顶圆**：22×22 与 `m(z+2)=22` 对上，是几何正确性的免费检查。

## 4. 折线还是样条：**用容差定，不要写死**

实测（m=1, z=20，轮廓周长 131.63 mm）：

| 分段数 N | 平均弦长 | 弦高误差（R=11 mm） | SW 草图实体 |
|---|---|---|---|
| 100 | 1.316 mm | **19.7 µm** | 100 |
| 200 | 0.658 mm | **4.9 µm** | 200 |
| 400 | 0.329 mm | **1.2 µm** | 400 |
| **700（当前默认）** | 0.188 mm | **0.40 µm** | **700** |

**结论**：当前默认**精度过剩、实体数过多**。700 条线段在 SolidWorks 里就是 700 个草图实体，建模、重建、导出、B-Rep 复核都会慢（归档代码自己也写了这条）。

**规则**：由调用方给 `chord_tolerance_um`，反算 N：

```
N ≈ 周长 / sqrt(8 · R · tol)
```

| 目标容差 | 建议 N | 适用 |
|---|---|---|
| 5 µm | **200** | 一般装配 / 示意（默认值） |
| 1 µm | **440** | 加工件、线切割 |
| 0.4 µm | 700 | 只在需要与**渐开线解析值**比对时用 |

> 注意：弦高 5 µm 已经远大于 §3.1.1 里「20 段圆弧 ≈ 0.22 µm」的近似误差，**所以真正的瓶颈是分段数，不是"折线 vs 圆弧"**。

## 5. 里程碑

| # | 内容 | 完成判据 | 依赖 |
|---|---|---|---|
| **M0** ✅ | 计划层（纯数据 + 预期体积/包围盒） | 17 条测试全绿，无 COM 依赖 | v0 齿轮方法层 |
| **M1** | **直齿轮真机跑通** | L3：实测体积与预期偏差 <1%，包围盒 = 22×22×10；L4 三视图目视；`level` 从 `stitched` → `verified` | M0 + 真机 |
| **M2a** | **轴**（旋转体） | 同构最简，验证 execute 抽象是否够用 | M1 |
| **M2b** | **同步带轮 / 链轮 / V 带轮** | 轮廓+拉伸+沟槽，与齿轮同构；齿形按标准表 | M1 |
| **M2c** | **花键** | 内/外方向是最大坑（易写反） | M2b |
| **M3** | **螺纹 / 弹簧**（螺旋 + 扫掠） | 单独评估：SW 的 helix+sweep 组合历史上不稳 | M2 |
| **M4** | 与工程图 / 装配接 | 出图与装配不动方法层 | M2 |

**为什么 M2a 先做轴**：轴是全族里**唯一不含标准表、不含齿形**的纯几何体（旋转）。用它验证 `execute()` 抽象够不够，比拿齿轮验证便宜——齿轮失败时分不清是抽象的问题还是齿形的问题。

## 6. 各族的建造难度（决定排期）

| 族 | 几何构成 | 难度 | 主要风险 |
|---|---|---|---|
| **轴** | 旋转（轮廓 + revolve） | **低** | 台阶/退刀槽的草图约束 |
| **圆柱齿轮** | 闭合轮廓 + 拉伸 | 中 | 分段数；齿根过渡 |
| **带轮 / 链轮 / 同步带轮** | 闭合轮廓 + 拉伸 + 沟槽 | 中 | 齿形标准表；槽深 |
| **花键** | 轮廓 + 圆周阵列 | 中 | **内/外方向极易写反** |
| **钣金 / 焊件 / 管路** | 原生特征 | **低**（已有模块） | 无 |
| **螺纹** | 螺旋线 + 扫掠切除 | **高** | SW helix+sweep 不稳；收尾/退刀槽 |
| **弹簧** | 螺旋线 + 扫掠 | **高** | 同上；变节距 |
| **凸轮 / 连杆** | — | **不做**（无成熟数学，见 07 分流表「放一放」） | — |

## 7. 每族同一套验收判据

| 层 | 判据 |
|---|---|
| **契约测试** | 无 COM，纯数据；单位量级断言；预期体积可复算 |
| **L3** | 实测体积 / 包围盒 vs 计划值，偏差 < 1% |
| **L4** | 导出 PNG 三视图，**用眼睛看**（重点看悬空草图与缺面） |
| **证据** | `evidence()` 齐：输入、解析尺寸、近似方式、分段数、**未覆盖清单** |

**没有 L3 的族一律 `stitched`。** 这条不是形式——归档的 `sw_gear.py` 就卡在这里。

## 8. 风险清单

| 风险 | 已经发生过的证据 | 处置 |
|---|---|---|
| **单位 1000×** | 归档代码：实物包围盒 0.0039×0.0076 mm | plan 内一律 mm；`to_meters()` 单点；测试断言坐标量级 |
| **草图实体爆炸** | 实测 700 条线段/件 | 由容差反算 N，默认 200 |
| **`AddToDB` / `DisplayWhenAdded` 没还原** | 归档代码用 try/finally 包了 | execute 必须同款 |
| **中文路径** | 项目已知坑（SW 会丢路径） | 中间文件落纯 ASCII 临时目录 |
| **COM 单进程** | 项目已知事实 24 | 不并发放同一次建模 |
| **helix+sweep 不稳** | M3 才碰，但要知道 | M3 单独评估，不排进主链 |
| **折线 vs 样条** | 归档只用折线 | 若 M1 发现性能不可接受，改样条需重做容差模型 |

> **造件不是"画出形状"，是"先算准、再计划、后执行、终核对"。**
