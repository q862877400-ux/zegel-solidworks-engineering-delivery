# Feature Specification: P3 · 并入模板定型（**改判据版**）

**Feature Branch**: `002-merge-template`

**Created**: 2026-10-01 · **Revised**: 2026-10-01（前提被证伪，见下）

**Status**: Draft

**Input**: User description: "P3 —— B 级并入的模板定型：最小的四个域（焊件 / 模具 / 参考几何 / 仿真）"

---

## ⚠️ 修订说明（**本 spec 的第一版前提是错的**）

**第一版**写的是「把焊件域搬进来」。**动手第一步就证伪了它**：

```
第一版的前提：焊件是本仓库的缺口（地图：⑧ 焊件 | 本仓库 ·（零）| 缺 5）
事实：        本仓库**早就有** scripts/sw_weldment.py —— 666 行 / 20 个函数，
              且用的是正确的官方名（InsertWeldmentFeature / InsertWeldmentCutList2 /
              InsertSubWeldFolder2 / CreateStructuralMemberGroup + CreateDefinition + CreateFeature）
```

**⇒ 根因是广度地图的计数口径错了。** `tools/build_union_map.py`：

```python
def _our_tools() -> list[str]:
    """本仓库 MCP 暴露的工具名（从 server.py 静态抽取）。"""
    server = ROOT / "mcp-server" / "server.py"
```

**⇒ 地图的「本仓库」列只数 `mcp-server/server.py` 里的工具名。**
而本仓库的能力实现在 **74 个 `scripts/sw_*.py` 模块 / 626 个公开函数** 里，
**它们没有被暴露成 MCP 工具**（AGENTS.md 已知事实 25 记的正是这个交集为 0 的结构性问题）。

**实证矛盾（逐域核过）**：

| 域 | 地图说「本仓库 \| 缺」 | 实际有什么 |
|---|---|---|
| ⑧ 焊件 | `·`（零）\| 缺 5 | **`sw_weldment.py`（666 行 / 20 函数）** |
| ⑦ 钣金 | `·`（零）\| 缺 11 | `sw_sheet_metal.py` |
| ③ 草图 | 0 \| 缺 42 | `sw_sketch.py` + `sketch_relations.py` |
| ⑬ 仿真 | 2 \| 缺 4 | **6 个** simulation 模块 |
| ⑪ 工程图 | 3 \| 缺 49 | **4 个** drawing 模块 |
| ⑥ 曲面 | 2 \| 缺 12 | `sw_surface.py` + `advanced_surface_ocp.py` |

**⇒ 「339 缺口」的正确读法**：那是「**四家以 MCP 工具暴露、而本仓库没有以 MCP 工具暴露**
的操作数」，**不是**「本仓库缺 339 个能力」。

**⇒ 若不改判据就开工，会把已实现的能力当缺口重复搬一遍** —— 既浪费，又会造出第二份实现
（违「一个事实一个家」）。

---

## 修订后的目标

**本特性改为做三件事，按价值排序：**

1. **把「真实能力缺口」量出来**（按能力而非工具名），替代错误的 339
2. **找出**真正的**缺口域，并入其中一个作为模板**（而不是搬已有的焊件）
3. **把「已有能力 → MCP 工具」的转化路径厘清**（已知事实 25 的那个交集 0）

---

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 得到一个**口径正确**的缺口数字 (Priority: P1)

规划者需要一个能据以开工的数字。当前的 339 是「MCP 暴露面之差」，
**不能**用来决定「该实现什么」。

**Why this priority**: 这是**判据本身**。判据错，后面 339 个单位的活全会歪。
ROADMAP 的调整机制明写：「验收判据被证伪 ⇒ 改判据或砍」。

**Independent Test**: 重跑一个新脚本，得到「按能力对照」的缺口表，
且该表能解释「为什么焊件不是缺口」（因为 `sw_weldment.py` 存在）。

**Acceptance Scenarios**:

1. **Given** 地图用的是工具名口径，
   **When** 建立能力口径的对照，
   **Then** 焊件 / 钣金 / 草图 / 仿真 / 工程图 / 曲面 六域的「缺口」应显著小于地图值，
   并给出各域「我们已有的模块与函数数」。
2. **Given** 两个口径的数字，
   **When** 写进文档，
   **Then** **两个数都保留、各自标注口径**，不互相替代（避免又一次误读）。

### User Story 2 - 并入一个**真的**缺的域 (Priority: P2)

**Why this priority**: 模板需要在一个**真缺口**上定型 —— 在已有域上「定型模板」是假的。

**Independent Test**: 所选域在 User Story 1 的能力对照表里「本仓库 = 0」。

**Acceptance Scenarios**:

1. **Given** 能力口径缺口表，
   **When** 选模板域，
   **Then** 该域满足：① 本仓库该域能力数为 0；② 至少一家来源有实现；③ 域的规模最小。
2. **Given** 选定的域，
   **When** 并入，
   **Then** 走完六条规则 + 来源头注释（含「来源写错的名字 → 官方真名」的更正说明）。

### User Story 3 - 厘清「已有能力 → MCP 工具」的转化路径 (Priority: P3)

**Why this priority**: 已知事实 25 说「我们补的 58 个模块一个都没进 MCP」是最大结构缺口。
**把已有的 626 个函数变成可用工具，比再搬 339 个更直接。**

**Independent Test**: 给出一个可行路径（含最小示例：把一个既有函数暴露成 MCP 工具）。

**Acceptance Scenarios**:

1. **Given** `mcp-server/server.py` 只引用 25 个模块，
   **When** 评估暴露路径，
   **Then** 给出具体的注册方式与代价评估（改哪个文件、有无门禁约束）。

---

### Edge Cases

- 能力口径怎么数？按「函数名」会重复计（同名函数在不同模块）；按「官方 API 覆盖面」更准但更难自动算。
- 一个域「我们有几个函数算覆盖」需要阈值 —— 1 个函数算不算覆盖了该域？
- 地图的错误是否也影响 `capabilities.yaml` 的 `level`？（不 —— 那个是逐条人工判的，不受影响）

---

## Requirements *(mandatory)*

- **FR-001**: 新口径必须**可重跑**，且不得删除旧口径的数字（两者并存，各标口径）。
- **FR-002**: 能力对照表必须逐域列出「本仓库已有模块名与函数数」。
- **FR-003**: 模板域的选择必须**有据**（在对照表里本仓库 = 0）。
- **FR-004**: 若发现某域我们其实已有实现，**必须在表里标出**，不得沿用旧结论。
- **FR-005**: 结论与更正必须写进长期记忆（已做）与 ROADMAP 的调整记录。
- **FR-006**: 不得为了「凑数」把已有模块重写一遍。

---

## Success Criteria *(mandatory)*

- **SC-001**: 存在一个可重跑的命令，输出「按能力对照」的逐域缺口表。
- **SC-002**: 该表的焊件行显示「本仓库已有 `sw_weldment.py`」，而非「缺口 5」。
- **SC-003**: 文档里「339」出现处**都带口径说明**（MCP 暴露面），无误读空间。
- **SC-004**: 模板域在本仓库的能力数为 **0**（有据可查）。
- **SC-005**: 五项门禁 + 全量回归与基线逐条相同。

---

## Assumptions

- 「按能力对照」的自动判定会有噪声；本特性接受**半自动 + 人工复核**，
  但必须**可重跑**（不然又是一次「报告计数不附枚举命令」的错）。
- 已实现的域（焊件等）**不再重写**；若要提升其 level，走「实测」而不是「重写」。
