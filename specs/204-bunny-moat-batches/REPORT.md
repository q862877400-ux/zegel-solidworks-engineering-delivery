## 〇、一句话

**这六件事都是「把散落的事实变成可逐条核对的表」，而且每一件都被三个不同模型的裁判改写过头条数字。**

## 一、定位：为什么要做这六件

它们是**支线**工作（另一个对话在做主线）。支线的定位是：
**只做可穷举、可逐条核、不需要判断力的批量辅助**，产出**可核对的表**给主线用。
判据设计、真机执行、门禁改动、提交 —— **都归主线**。

选这六件的标准是三条**同时成立**：

| 条件 | 依据（都实测过） |
|---|---|
| ① **我们有闸，别人不知道自己在错** | 本轮实测：Bunny **每一路都自称「已逐字校验」**，而引文逐字回查抓出 **11/7360 = 0.15%** 是编造的 |
| ② **我们已抽出语料，别人要重做** | 203 已产出：2839 份官方示例的成员索引（3985 个名）· 566 接口台账（11557 成员）· 8238+11117 两个官方名单 |
| ③ **有既有核验设施，能把活机械化** | `capabilities.yaml` 的 110+ 条 level+evidence · `signature-audit.md` · 官方三源 |

## 四、作业方式（**实测出来的硬约束，再派活请照做**）

| 约束 | 值 / 依据 |
|---|---|
| **批量子代理模型** | **只用** `opencode-zen` / `space-bunny-free`，且 `provider` 与 `model` **必须成对写**（只写 `model` ⇒ 整批静默失败，100 路回 `returned: 0`） |
| **DeepSeek 的用途** | **只做裁判**（抽检 + 审判据），**不做产出**（我犯过一次，把 V1 当产出方派了 60 路） |
| **一波路数** | **≤ 60**（实测 89 路死 19 ≈ 21%） |
| **一份文档一路** | 3 份合批的 8 个批次曾**全灭**；一份一路 38/38 |
| **每件第一步** | **5 路探针**；`returned: 0` 当失败查 |
| ★ **一个 job 别装多批** | **`parallel` 语义是"全等"，不是"尽力而为"** —— 一个 hang 的 agent **锁死整批**。第 6 轮我用「一个 workflow 串行跑 7 批」，它**卡了两轮没推进**；改成**每 30 箱一个独立 job** 后，**一轮从 240 推到 485** |
| **两道闸** | ① 引文**逐字回查**原文（挡掉 0.15% 编造）② 三裁判（不同模型 + 不同视角） |
