## 一、★★★★★ 目标（★ 逐字承计划 §5 EC02）

★★★ **用**审计过的算法和规则**回答「这样设计行不行」，★ **不让检索片段直接当规则执行**。**

★★ **一句话**：★ EC01 说「**要什么**」；★★★ **EC02 说「行不行」—— ★ 且**必须给得出出处**。**

## 二、★★★★★ 用户故事与验收场景

### US1（P1）★ 每条**硬规则**都能查到**出处与适用域**

★ 作为设计者，我要知道这条规则**从哪来**、**对什么适用**。

| # | ★ 验收场景 |
|---|---|
| S1-1 | ★ 每条规则必须带：★ **标准号 · 版本 · 条款号 · 效力状态 · 查证日期** |
| S1-2 | ★★ **缺出处 ⇒ 不得返回 `pass`**（★ 只能是 `unknown`） |
| S1-3 | ★ 适用域必须**显式**（★ 设备类别 / 材料 / 工况） |

### US2（P1）★ **过期 / 缺源 / 域外 / 统计假设缺失 ⇒ 一律不能通过**

★ 作为验收者，我不接受「差不多就行」。

| # | ★ 验收场景 |
|---|---|
| S2-1 | ★ **标准已废止**（★ 🔴）⇒ ★ 不得 `pass` |
| S2-2 | ★ **标准即将实施**（★ 🟡）⇒ ★ 不得当现行用 |
| S2-3 | ★★ **域外**（★ 设备类别不在适用域）⇒ ★ 不得 `pass` |
| S2-4 | ★★★ **统计假设缺失**（★ 如 RSS 没说分布）⇒ ★ 不得 `pass` |

### US3（P1）★ 算法有**不共享实现**的参考值

★ 作为审签人，我要知道**算法对不对** —— ★ 不是「跑出来就是这样」。

| # | ★ 验收场景 |
|---|---|
| S3-1 | ★ 每个算法必须**另有**一条独立复算路径（★ 不共享代码） |
| S3-2 | ★★ **参考值不得取自被测实现**（★ 承 EC00 的「双盲」纪律） |
| S3-3 | ★ 边界值 / 量纲 / 单调性 / 区间 都要查 |

### US4（P1）★ 规则决策**保留依据与反例**，★ **不搞多数投票**

★ 作为接手方，我要看到**为什么这么判**，★ 以及**什么情况下不成立**。

| # | ★ 验收场景 |
|---|---|
| S4-1 | ★ 每条判定保留**依据**（★ 出处 + 计算过程） |
| S4-2 | ★★ **矛盾规则按优先级和适用性处理** —— ★ **不能多数投票** |
| S4-3 | ★ 每条规则带**反例**（★ 什么情况下它会 fail） |

### US5（P2）★ 标准**版本变化** ⇒ 影响清单 + 证据自动标过期

★ 作为维护者，我要知道换版**影响了哪些结论**。

| # | ★ 验收场景 |
|---|---|
| S5-1 | ★ 版本变化必须产生**影响清单**（★ 哪些结论受影响） |
| S5-2 | ★★ **不能只改数据库版本号**（★ 那是「假装处理了」） |
| S5-3 | ★ 受影响的证据 ⇒ ★ **自动标 `expired`** |

### US6（P2）★ **未知类别 ⇒ 返回待澄清**，★ **不能「无标准适用」**

★ 作为使用者，我不要一个**沉默的通过**。

| # | ★ 验收场景 |
|---|---|
| S6-1 | ★ 建立**首个限定设备类别**的适用性矩阵 |
| S6-2 | ★★★ **未知类别 ⇒ `needs_clarification`** —— ★ **不是「无标准适用」** |
| S6-3 | ★★ **「无标准适用」是一种**判定**，★ 必须**有依据****（★ 不是默认值） |
