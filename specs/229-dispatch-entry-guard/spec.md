> 开工：2026-10-09（主任务 `ff6c7344` 第 3 轮）

## 一、要解决的问题（**靶子**）

`spec 228` 修好了 `call_assembly_doc` **一个**入口，并把教训写成一句通用话：
「**加新分发口时必须问一句：它进审计白名单了吗**」。★ **而一句话不是守卫**（事实 40：
一个存在但没人审的入口 = 没有守卫，且更糟 —— 让人以为防住了）。

本轮先**量**清这条边界的真实宽度（真树实测，`output/_probe229_buckets.py` 的结论）：

```
COM 包装器调用点总数                        1310
  · 字面量（成员名写在调用点 ⇒ 审计可见）     1219
  · 非字面量（审计一律看不见）                  91   ← 7 %
      ├ 形参转发（真「分发口」）                37   ← 本切片判它
      ├ 局部变量                                52
      └ 计算式                                   2
```

| # | 事实 | 后果 |
|---|---|---|
| 1 | `audit_byref_args` 只审**第二实参是字符串字面量**的调用点 | 91 个调用点（7 %）**从未被 by-ref 审计覆盖**，而**没有任何文件记着这个数** |
| 2 | 37 个「分发口」把成员名当**形参**转发（`_checked(target, member, *args)` 这类） | 228 只登记了其中 1 个（`call_assembly_doc`），其余 **36 个无任何表态** |
| 3 | 新增一个分发口**不需要**任何手续 | 228 的教训**只存在于散文里** ⇒ 下一个入口还会静默落进盲区 |

## 三、★ `exempt *` 的语义（**必须写清，否则会被读成「已验证安全」**）

`exempt` 的意思是「**已知盲区、登记在案**」，**不是**「这个入口的 by-ref 是对的」。

门禁保证的是：① 盲区被**枚举**；② 盲区**不会被悄悄扩大**（新增分发口 ⇒ 未表态 ⇒ 红）；
③ 每一条豁免声明**成立**（自证）。门禁**不保证**这 36 个入口的 by-ref 占位是对的 ——
那需要**逐个把调用方那一侧的实参接回签名**（下一轮的事，见 §五）。

## 四、★ 只报不判罪的两个桶（**本切片不做完，明确登记**）

- **局部变量 52 个**：`name = f"Get{X}"` 之类在函数内算出成员名 —— 静态审计同样看不见，
  但**逐个定性**（哪些能还原成字面量、哪些真的动态）需要人工判断 ⇒ 会变成半成品。
- **计算式 2 个**：成员名是表达式/属性。

⇒ 本切片对这两个桶**只计数 + 冻结下界**（FR-006），**不要求声明**。这是**明确划出的边界**，
不是遗漏；下一轮若要收，先开新 spec 并**先量**。

## 五、不做（明确边界）

- 不连 COM / 不碰真机（本切片纯静态）。
- 不改 `audit_byref_args.py` / `audit_call_arity.py` 的**任何逻辑**（口径与它同源，只 import）。
- 不把「豁免」改成「已验证」：**不解析**调用方实参 ↔ 形参的对应（那才是真正的修复，另立 spec）。
- 不给 52 + 2 两个桶加声明（§四）。
- 不处理别名导入（`from ... import call_assembly_doc as cad`）—— 仓库当前无此写法。
