# 203 · 支线批量作业：用并行免费 AI 做「可回查原文」的穷举活（五批）

**Status**: Planning（2026-10-04 立）

> **定位**：这是**支线**（`docs/kickoff-bunny-sideline.md` 定义的那种活）的规格。
> 支线**只做可穷举、可逐条核、不需要判断力**的批量辅助；判据设计 / 真机执行 / 门禁改动 / 提交
> **仍归主线**。本文档是支线自己立的规格，用来让主线**看得见、用得上、能复算**。

## 一、为什么要立这份规格

本项目反复栽在同一处：**判据交出去批量执行，能拿到我自己读不出来的样本量**。
已发生的两次：
- 上一批 **100 路**扫描 → Bunny 一致报出**四个判据系统性缺陷**（`docs/recon/family-scan-100-criteria-defects.md`）；
- 2026-10-04 支线 A/B/C 三件 → 抄出 472 个官方成员页、
  **实测发现指针判据大小写敏感会漏计**（官方原文有 `In-process` 大写 I）、
  并挡住 Bunny 对 `docs/metrics.md` 的 **5 条编造**（`1132` 等，`grep` 零命中）。

⇒ **本规格把这类活固定成可复算的五批**，每批都写明「读什么 / 抄什么 / 判据 / 产出 / 限度」。

## 二、五批（按「价值 ÷ 可核性」排序，顺序执行）

| 批 | 名称 | 读什么 | 抄什么 | 判据可核性 | 规模 |
|---|---|---|---|---|---|
| **B1** | `verified` 证据回读 | 121 个能力条目 + 各自 `evidence` 点名的文件 | `level` vs 证据**是否可达** + 证据**自己的 verdict/通过数** | ★★★ 纯机械 | 121 路 |
| **B2** | 官方源自身的错 | 566 个接口目录的全部成员页 | 页内自相矛盾 / 死链 / 枚举声明数与实际不符 / 拼写错 | ★★★ 纯机械 | 566 目录 |
| **B3** | 官方示例的**调用序与前置** | `C:\swapi\examples\` 2839 份示例 | 调用**顺序** · 每步**前置** · 单位写法 | ★★ 引文可回查 | 2839 份 |
| **B4** | 成员 → 示例可达索引 | 同 B3 的 2839 份**正文** | 每份**实际调用**的成员名 | ★★★ 名字须在 8238/11120 名单里 | 2839 份 |
| **B5** | 全量接口台账 | `C:\swapi\types\*` 11557 个成员页 | 签名 / `I` 前缀成对 / `out`·`ref` 参数 / 指针 / 废弃 | ★★★ 已在本机验证过解析器 | 566 目录 |

**为什么 B1 排第一**：仓库**自己已经承认过一次**这类缺陷 ——
`capabilities.yaml` 有一个条目**唯一真机证据顶层写着 `"verdict": "fail"`、`passed: 9 / total: 12`，
而 `level` 仍写 `verified`**（已降级）。**但那是手工撞见的。**
⇒ B1 直接回答「**97 条 `verified` 站不站得住**」，而这是本仓库可信度的地基。

## 三、B1 详规（第一批，先做）

### 3.1 输入
- `capabilities.yaml`（**4403 行 / 121 个条目**；`"level": "verified"` **97** 条、`stitched` **11** 条；
  **107** 条带 `evidence` 字段）。条目结构已实测确认：
  ```
  { "id": …, "label": …, "level": "verified", "backends": [...],
    "verified_versions": [...], "limitations": [...], "allowed_modes": [...],
    "evidence": ["pytest tests/test_xxx.py", "output/xxx.json"], "source": … }
  ```
- 每条 `evidence` 是**具体可读的**（测试文件路径 / `output/*.json` 证据）。

### 3.2 抄什么（每条一个 JSON）
| 字段 | 含义 |
|---|---|
| `id` / `level` | 照抄条目里的 |
| `evidence_total` | `evidence` 数组长度 |
| `evidence[]` | 每项：`raw`（照抄原文）· `kind`（pytest / json / py / md / 其它）· `path`（解析出的路径）· `exists`（**文件真的在不在**）· `verdict` / `passed` / `total`（**证据文件自己写的**，没有就写「查不到」）|
| `level_supported` | `"yes"` / `"no"` / `"cannot_tell"` —— **只判「证据自己有没有说它失败」**，不判能力好不好 |
| `contradiction_note` | 若 `level=verified` 而证据顶层 `verdict` 是 fail/False ⇒ 写清哪一条、原文是什么 |
| `unreachable` | 列不可达的 evidence 路径（**这是最硬的缺陷**：证据不存在）|

### 3.3 判据（机械，非主观）
| ID | 判据 | 怎么算 |
|---|---|---|
| SC-20301 | 每条 `evidence` 的路径**存在性**被真判过 | 文件系统 `exists`，不许推测 |
| SC-20302 | 证据**自己写明的** `verdict`/`passed`/`total` 被逐字抄回 | 从 JSON 顶层字段读，不解析散文 |
| SC-20303 | `level=verified` 且证据顶层 `verdict` 为失败 ⇒ **必须**出现在矛盾清单 | 字符串比对 |
| SC-20304 | **两条独立路径**报同一结论才进主表（引文核验 + Lead 抽查） | 见 §四 |
| SC-20305 | 产出**不含行号**（行号会漂，实测偏过 47 行），只给文件名 + 可 `grep` 片段 | — |
| SC-20306 | 不可达路径**单列一节**，不混进主表凑数 | — |

### 3.4 产出
- `docs/recon/verified-evidence-audit-2.md`（**主产出**，主线直接读）
- `specs/203-bunny-sideline-batches/recon/b1-*.json`（Bunny 逐条原始产出，可复算）

## 四、作业方式（**实测出来的三条硬约束**）

| 约束 | 实测依据 |
|---|---|
| **子代理一律 Bunny**（`provider: "opencode-zen"` + `model: "space-bunny-free"`，**必须成对写**） | 只写 `model` 会**整批静默失败**（100 路回 `returned: 0` 且无报错） |
| **一波 ≤ 60 路** | 实测 89 路时死 19（**21% 失败率**）；70 路时死 19/70；**单文档形态 38/38 零失败** |
| **一份文档一路** | 3 份文档合批的 **8 个批次全灭**；改成一份一路后 38/38 |

> ★ **先 5 路探针再铺量**：探针验不过就不铺。

## 五、每批都必须做的两道闸（缺一不可）

1. **引文逐字核验**：每条 `quote` 回查**是否真在原文里**，不通过一律剔除。
   **实测必要性**：Bunny 对 `docs/metrics.md` 编造过 **5 条**（`1132/889/1297/1981/249`，原文零命中）。
2. **Lead 抽查**：随机抽 5–12 条复核引文与理由。
   **实测有效性**：C 批抽查 12/137，全部对得上；并另做「同单位 40 条」**主动找茬**，未发现漏判。

## ⚠ 明确记下的限度（不许含糊）

* ⚠ **假阴性可以存在**：配对/抽取只用了字面判据 ⇒ 两份文档用**完全不同措辞**说同一个量时抓不到。
  产出**不能**被读成「没有问题」，只能读成「在**这套判据**下、对**这些条目**没发现问题」。
* ⚠ **Bunny 会编造**（已实测 5 条）⇒ 它的产出**不许**直接进 `capabilities.yaml` 或任何 `verified`。
* ⚠ **判定权在主线**：支线只报**事实与候选**，不改 `level`、不改判据、不动门禁。
* ⚠ **支线不跑真机**（不碰 SolidWorks / COM）、**不跑 git**。
