# 需求说明：DSH 在 1000+ 工具规模下的工具调用

> 这份文档只写【业主的诉求】与【已实测的事实】，不含任何设计主张。拿去问别人时可直接给对方。

---

## 一、背景

**系统**：DeepSeek Harness（DSH）。工具来自 MCP server 与插件，
以 JSON Schema 形式放在**每一次请求的 `tools` 字段**里发给模型。

**工具数量的现实规模**：平时单会话 **77 ~ 116** 个；有会话挂到 **589** 个；★ **目标场景 1000+**。

---

## 二、诉求

### 硬指标

**R1 —— 1000+ 工具时，仍能【准确】调用工具。**
- 选对工具、参数填对
- ★ 不是「少调几个也行」，而是**全部工具都要可用、都能被选中**

**R2 —— 不影响 AGENTS.md（系统提示 / 指令区）的遵循度。**
- 工具数量涨到 1000+ 时，**指令的遵循度不能下降**

**R3 —— ★ 不允许用「让用户预先分类、按需挂载」来回避问题。**
- 业主原话：**「我要能减我直接用标准模式不就行了」**
- 即：**1000+ 工具必须同时处于可用状态**，不能靠「这次只挂一部分」来解决

### 软指标

**R4 —— 在不影响 R1/R2 的前提下，能省一点上下文更好。**
- 业主原话：**「节约 token 只是顺手的事情又不是硬指标」**

---

## 三、已实测的事实（供对方判断）

### 3.1 工具定义每一轮都注入，是常量

| 会话 | 工具数 | 工具字节 | 首轮工具占请求 | 末轮工具占请求 | 末轮总请求 | 末轮 input token |
|---|---|---|---|---|---|---|
| A | **589** | **174 KB** | ★ **50%** | 10% | 1,671 KB | **235,674** |
| B | 77 | 27 KB | 27% | 2% | 1,488 KB | 183,754 |
| C | 77 | 27 KB | 27% | 3% | 1,085 KB | 131,896 |

★ 占比随对话变长而**下降**，但那只是**分母（历史）变大** —— 工具的**绝对量一点没少**。
会话 A 的 71 步里，那 174 KB 被发了 **71 次**。

### 3.2 那 174 KB 里是什么

官方 72 个工具的解剖（DSH 自己发布的那批工具）：

| 组成 | 字节 | 每工具 | 占比 |
|---|---|---|---|
| 工具级 description（怎么用 / 何时用） | 16,886 B | 235 B | **39%** |
| 参数级 description（单位 / 默认值） | 14,365 B | 200 B | **33%** |
| 参数结构（type / enum / required） | 10,124 B | 141 B | 24% |
| 参数名 | 1,660 B | 23 B | 4% |

⇒ **描述类合计 73%，结构类 27%。**

### 3.3 「不丢信息、只换编码」能省多少（实测上限）

| 投影 | 字节 | 每工具 | 信息 |
|---|---|---|---|
| JSON Schema（native 走这条） | 58,626 B | 814 B | 全量 |
| TypeScript SDK（PTC 走这条） | 51,772 B | **719 B** | 全量（描述变 JSDoc） |

⇒ ★ **换编码只省 11.7%。** 官方源码自述两者是 *two projections of the same store*。

### 3.4 官方在「另一种能力」上的先例

**Skill**：目录只放 `name` + `description`（上限 500 字符），**正文按需加载**。
（`docs/subsystems/skills.md`：The catalog contains … name and normalized … description only; it omits bodies, paths, sources, providers, and routing hints.）

### 3.5 DSH 现成的能力（公开 API，不需改核心）

- `ctx.tools.register(definition) → disposer` —— **可动态添加 / 移除单个工具**
- **Scoped restriction** —— 可**按 agent 限定可见的工具集**
- `system-prompt/assemble` 是瀑布，**返回值即权威** —— 可在装配时改写发给模型的工具列表

---

## 四、已明确排除的方向

| 方向 | 为什么被排除 |
|---|---|
| **砍 schema / 压缩描述** | 牺牲 R1（实测端到端可调用 **89.9% vs 95.0%**） |
| **往指令区加工具目录 / 索引** | 违反 R2（指令区不该被工具内容占用） |
| **按需分组挂载（预设分组）** | 违反 R3 |
| **PTC / code 模式** | 其 SDK 段同样 O(N)（719 B/工具），解决不了工具太多 |

---

## 五、成功判据（请对方给出可测的定义）

1. **工具调用准确率**：1000+ 工具下，「选对工具 + 参数通过真实 schema」的比例，**不低于**现在 84 工具时的水平（baseline 待补测）
2. **指令区字节数**：**不随工具数量增长**
3. **全部工具可达**：任一工具**不因机制设计而变得不可被选中**
4. **上下文**：在满足 1–3 的前提下，越小越好

---

## 六、一句话

> **1000+ 个工具同时挂着，模型还能准确挑对、参数填对；同时 AGENTS.md 的遵循度不被工具定义稀释；不许用「少挂几个」来回避。**
