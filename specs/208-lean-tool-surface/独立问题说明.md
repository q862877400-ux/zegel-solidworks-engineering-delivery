# 上千个工具同时挂载时，如何保持 LLM 智能体的调用准确与指令有效

**一份完全自包含的问题说明。**
读者不需要本项目的任何背景、任何文件、任何前置知识。

---

## 0. 问题陈述（其余章节都是它的展开与证据）

> 一个基于大语言模型的编码智能体，当它可见的工具从几十个增长到 **一千个以上** 时，会出现两件事：
>
> 1. **模型挑错工具**，或者反复使用它熟悉的那几个，完全想不到冷门工具；
> 2. **系统的行为指令失效** —— 模型不再严格遵守事先写好的规则。
>
> 这两件事 **根因相同**：工具定义是 **每一次请求都要重发的常量**，它占据了大量上下文，把系统指令稀释掉了。
>
> **要求**：一千个工具 **必须同时可用**（不接受「每次只挂一部分」这种回避），
> 在此前提下把调用准确率维持在几十个工具时的水平，并保证系统指令的效力不下降。
> **节省 token 是次要加分项，不是目标。**

## 1. 背景：LLM 智能体是怎么使用工具的

### 1.1 工具调用（function calling）是什么

现代 LLM 的 API 允许调用方在请求里附上一份 **工具清单**。每个工具是一个 JSON Schema，形如：

```json
{
  "name": "export_drawing_pdf",
  "description": "Exports drawing sheets to a PDF file. Sheets default to every sheet in the drawing.",
  "parameters": {
    "type": "object",
    "properties": {
      "output_path": { "type": "string", "description": "Absolute path of the PDF file to write." },
      "dpi": { "type": "number", "description": "Raster resolution in dots per inch, from 72 to 1200; defaults to 300." }
    },
    "required": ["output_path"]
  }
}
```

模型看到这份清单后，可以（在回复里）输出一次 **结构化的调用**：选哪个工具、传什么参数。
真正执行由 **宿主程序**（下文称 harness）完成 —— 模型自己碰不到外部世界。

### 1.2 关键事实一：工具定义 **每一次请求都要重发**

这是 API 层面的机制，不是某个实现的选择：

- LLM 是 **无状态** 的：每次请求都要把 **完整对话历史 + 完整工具清单** 一起发过去；
- 因此一次会话有 N 轮交互，工具清单就被 **原样重复发送 N 次**。

### 1.3 关键事实二：上下文窗口是 **共享预算**

模型的上下文窗口是一个总预算，下面这些东西 **共用** 它：

```
[ 系统指令 / 规则 ]  +  [ 工具定义 ]  +  [ 全部对话历史 ]  +  [ 当前输入 ]
     固定的小块            固定的大块         随对话增长
```

- 工具定义占得越多，**留给指令与对话的空间越少**；
- 工具定义是 **常量**，它 **不会** 因为对话变长而消失。

### 1.4 为什么工具数量会影响表现

**现象 A —— 选择准确率下降。**
候选越多，模型越难挑对。典型表现：挑错相似工具；**只反复用它熟悉的那几个**，
即使存在更合适的冷门工具也想不到。

**现象 B —— 指令遵循度下降。**
系统指令（编码规范、工作流纪律、红线）在上下文里是很小的一块。
当上下文被大量与指令无关的内容占据，模型对指令的注意力被稀释，
表现为：忽略规则、跳过流程、忘记约束。

⇒ ★ 工具定义不是「多占点地方」那么简单，它直接损害智能体的可靠性。

## 2. 涉及的系统

**DSH（DeepSeek Harness）**：一个开源的 LLM 智能体框架（编码智能体方向）。
设计上是「一切皆插件」：模型、工具、沙箱、会话存储、界面都可替换。

与本文相关的三点：

1. **工具来自插件与 MCP server。**
   MCP（Model Context Protocol）是让外部进程以标准方式对外暴露工具的一套协议。
   一个 MCP server 可能一次提供几十上百个工具 —— 例如某 CAD 软件的自动化接口暴露 253 个。
2. **工具定义、系统指令、对话历史在 API 上是分开的字段**，
   但在模型看来 **共用一个上下文窗口**（见 1.3）。
3. **框架提供了运行时动态增删工具的接口**（见第 7 节），
   所以「在一轮里改变模型可见的工具集」在技术上是可能的。

## 3. 实测数据

> 来源：从该框架 **真实会话记录** 中读出每一次请求的 `tools` 字段与 API 返回的 token 用量。
> 这些数字不是估算，是框架自己落盘的事实。测量方法见附录 A。

### 3.1 实际的工具规模与会话开销

| 会话 | 挂载工具数 | 工具定义字节 | 首轮中工具占比 | 末轮中工具占比 | 末轮请求总字节 | 末轮输入 token |
|---|---|---|---|---|---|---|
| A | **589** | **174 KB** | ★ **50%** | 10% | 1,671 KB | **235,674** |
| B | 77 | 27 KB | 27% | 2% | 1,488 KB | 183,754 |
| C | 77 | 27 KB | 27% | 3% | 1,085 KB | 131,896 |
| D | 77 | 27 KB | 27% | 2% | 1,362 KB | 148,360 |

**读法**：

- 平时会话挂 77 个工具，**开局请求就有 27% 是工具定义**；
- 挂到 589 个时，**开局 50%**，且该请求已需 **108,721 token**（按 100 万窗口计，占 11%）；
- 到末轮，该会话每次请求要 **235,674 token**，占窗口 **23.5%**。

### 3.2 一个容易误读的点：占比下降不等于成本下降

上表里「末轮只占 10%」看着比首轮的 50% 好，但这是 **假象**：
工具定义 **每一轮都原样发送**，绝对量没变；占比下降 **只是因为对话历史把分母撑大了**。

会话 A 共 71 轮，那 174 KB 的工具定义被 **重复发送了 71 次**。

### 3.3 那 174 KB 里具体是什么

对框架自己发布的 72 个工具的定义做逐字段解剖：

| 组成 | 合计字节 | 每工具 | 占比 |
|---|---|---|---|
| 工具级 description（做什么、何时用） | 16,886 B | 235 B | **39%** |
| 参数级 description（用途、单位、默认值） | 14,365 B | 200 B | **33%** |
| 参数结构（type / enum / required） | 10,124 B | 141 B | **24%** |
| 参数名 | 1,660 B | 23 B | 4% |

⇒ ★★ **描述性文字合计占 73%，参数结构只占 27%。**

### 3.4 「只换编码、不丢信息」能省多少（重要）

同一个工具集，用两种编码表达 **完全相同的信息**：

| 编码 | 合计字节 | 每工具 | 信息量 |
|---|---|---|---|
| JSON Schema（function calling 的标准形式） | 58,626 B | 814 B | 完整 |
| TypeScript 类型声明（同框架另一模式采用的） | 51,772 B | **719 B** | 完整（描述变注释） |

⇒ ★★ **换一种更紧凑的编码，只省 11.7%。**
（框架源码原话：两者是 two projections of the same store。）

⇒ **推论：不存在「保持信息不变还能大幅缩小」的编码技巧。**
   参数信息必须抵达模型；无论怎么编码，其规模都与 **工具数量成正比**。

## 4. 问题陈述（数据版）

**目标场景**：一次智能体会话里，**一千个以上工具同时处于可用状态**。

**按上面数据推演**：

- 589 个工具已让开局请求 **50%** 是工具定义、总请求逼近 **24 万 token**；
- 一千个以上时，工具定义本身将达 **300 KB 量级**（按 3.3 的每工具字节推算）；
- 而系统指令通常只有 **几万字节**。

⇒ ★ **1.4 的两个现象会同时发生：挑错工具 + 指令失效。**

**难点在于两个约束互相冲突**：

- 要让模型 **填对参数**，参数信息 **必须出现在上下文里**（无法靠更紧凑的编码绕开，见 3.4）；
- 要让模型 **遵守指令**，上下文里的 **非指令内容必须尽可能少**。

## 5. 需求

### 硬性要求

**R1 —— 一千个以上工具同时可见时，调用仍然准确。**
选对工具、参数填对。**全部工具都必须可用、都能被选中**，不接受「用不到那么多」。

**R2 —— 系统指令（AGENTS.md）的遵循度不能下降。**
工具数量增长时，指令的效力必须保持。

**R3 —— 不允许用「预先分类 / 每次只挂一部分」来回避问题。**
如果「少挂几个」就能解决，那用标准模式就够了，不必专门做这件事。
即：**一千个工具必须同时可用**。

### 次要目标

**R4 —— 在满足 R1/R2 的前提下，若能顺带减少 token 消耗更好。**
（注意：是「顺带」。任何为了省 token 而牺牲 R1/R2 的方案都不接受。）

## 6. 已排除的方向（已实测或已论证，请不必再提）

| 方向 | 排除理由 |
|---|---|
| **裁剪 / 压缩工具描述与 schema** | 直接牺牲 R1。实测端到端可调用率：裁剪后 **89.9%** vs 完整 **95.0%** |
| **在系统指令里追加工具目录 / 索引** | 直接违反 R2 —— 那正是把工具描述搬进指令区 |
| **预先分组、按需挂载（模式分组）** | 违反 R3 |
| **改用「写代码调用工具」的模式** | 该模式的类型声明段 **同样是 O(N)**（实测 719 B/工具），没解决工具太多 |
| **换更紧凑的编码** | 实测只能省 11.7%（见 3.4），量级不够 |

## 7. 目前已知可用的机制（供方案设计参考）

该框架已提供、且 **不需要修改框架核心** 的能力：

1. **运行时注册 / 注销单个工具**：

   ```ts
   ctx.tools.register(definition)   // 返回一个 disposer，调用它即注销该工具
   ```

2. **按 agent 限定可见工具集**（框架内称 scoped restriction）：同一进程内不同 agent 可有不同工具集。
3. **在「装配系统提示」这一环节改写发给模型的工具列表**：
   该环节是一条可拦截的流水线，**返回值即权威**，因此可在此增减工具。
4. **工具可被动态发现**：工具仍全部注册在框架里，只是可以决定「这一轮让模型看见哪些」。

此外，该框架在 **另一个能力（Skill）** 上已采用一种可类比的模式：
**Skill 的目录只放名字与一句话描述，正文在模型主动调用时才加载。**
（框架文档原话：目录只含 name 与规范化后的 description，**不含正文、路径、来源、提供方**。）

## 附录 A：数据是怎么测的

- **数据源**：框架自己落盘的会话记录（每次请求的 `tools` 字段、每次 LLM 调用的 token 用量）。
- **工具占比** = 工具定义字节 ÷（工具定义 + 系统指令 + 截至该轮的对话历史）字节。
- **token 用量** 直接取 API 返回的 usage（输入 token + 缓存读取 token）。
- **3.3 的解剖** 是对框架自己发布的 72 个工具的 JSON Schema 逐字段归类求和。
- **3.4 的两种编码** 均由框架自身代码生成（同一份 schema 的两个投影函数）。

## 附录 B：为什么「占比会下降」这件事值得单独说

讨论「工具占用」时，常见做法是给出一个 **平均值或末轮值**，据以认为影响不大。
但工具定义是 **常量**，它在 **每一轮** 都完整存在。
真正决定指令是否失效的，是 **单个请求里工具定义相对于指令的体量**，而不是它与整场对话的比例。

⇒ 请以 **单轮** 为口径评估，不要以整场对话的平均值评估。
