## 〇 · 本轮确立的三条**作业方式**（业主 2026-10-03 指示）

| 方式 | 具体做法 | 为什么 |
|---|---|---|
| **M1 · 三路取优** | 每个**核心**工作项 ⇒ **派 3 个 bunny 独立做**（角度必须不同）⇒ 第 4 个 bunny 当**裁判**逐份评分、选胜者、并指出「该把落选者的哪些片段拼进来」 | 业主原话：「很浪费但是效果好」；★ 实践已证：L3 档 bunny 揪出过我的真 bug |
| **M2 · 铺张使用免费模型** | bunny **免费** ⇒ 大量派它做「**很有用但平时成本高**」的活：**全面扫描 / 全面阅读 / 穷举核对 / 多角度重做** | 这些活以前因为贵而**被跳过**，现在是净收益 |
| **M3 · 核心质量不外派** | 判据设计 · 真机执行（COM 单源）· 门禁本体 · 已知事实 · **提交** —— **一律 Lead 自己做** | 业主原话：「核心质量的问题一定要自己把握好」 |

★ M2 与 M3 的**分界线**：**能机器复核**的可以派；**判"什么算对"**的不能派。
★ M1 的**成本控制**：三份候选**写成三个文件**、由裁判读文件出短评 ⇒ ★ **不把三份代码灌进 Lead 上下文**。

## 三 · 每条产出的**验收出口**（不许只说"做完了"）

1. **能机器核的判据**：`ast.parse` / `release_check` / `check_union_conventions.py` / 覆盖率脚本 / 探针 JSON 读数。
2. **真机证据**：`output/*evidence*.json`，且**判据含可回读的量**（★ 不只"特征树增量"—— 事实 486）。
3. **如实记否定结果**：做不到就写「做不到 + 卡在哪 + 已排除哪些路」，★ **不许**写成"能"。
4. **收尾链**：`pwsh -File tools\round_chain.ps1 -Tests tests\<相关>.py`，★ 要求 `release_check 第 1 轮 OK`。
5. **提交**：`git commit -F <msgfile>`，★ 提交信息里写**机制与依据**（不是"改了什么"，而是"为什么").
