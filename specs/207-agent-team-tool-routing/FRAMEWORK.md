## 〇、一句话框架

> **lead（主刀医生）独占 COM 并持有施工计划；若干「器械护士」持有工具知识、只回文字不碰 COM；
> lead 每走一步向护士问「用什么工具」，护士回答带上签名/前置/已知冲突；每步回读模型状态写进进度表。**
>
> ★ 核心不是「把工具分给多个 agent」，而是 **把「决定」与「执行」分开**：
> **决定可以并行/复制/用便宜模型，执行必须串行**（COM 是单源）。

## 二、方案选型（✅ 已定）

### 2.1 两个候选方案

| | 方案1 · 工具分给各专家 | 方案2 · lead 主刀 + 器械护士 | |
|---|---|---|---|
| 做法 | 每个专家的 `agents.md` 里塞 X 个 MCP 工具，靠原生能力调 | lead 独占 COM；护士只回文字（工具名+参数） | |
| 解决什么 | 每个专家**带的工具少** | ✅ **结构性消掉 COM 争抢**；路由表**只存在 lead 一处** | |
| 没解决什么 | ❌ **COM 争抢**；跨域接力**分摊到 N 个专家**（要 N 份路由知识） | ❌ lead 成为单点；上下文压力 | |
| 落地成本 | ★ **必须改插件**（角色表现在只有减法 `denyTools`） | ★ **零插件改动**（护士根本不挂 MCP 工具） | |

### 2.2 ✅ 决策：**以方案2 为骨架**

**理由（三条，都有依据）：**

1. ★ **COM 是串行物理资源**（本仓已知事实 24：**运行时只能有一个 SolidWorks MCP，多个进程抢同一 COM 连接会死锁**）
   ⇒ 「谁能调」不稀缺，「**谁能决定**」才稀缺 ⇒ **决定与执行分开是正确的分解，不是妥协**。
2. ★ **本仓最难的实测问题是「选择」**（21 个 `simulation_apply_*` 的 **BM25 top-5 = 40%**），
   而那是**决定**问题 ⇒ **护士不碰 COM 就能解**。
3. ★★ **本仓已经有「器械护士」的半成品**：`AGENTS.md` 2026-10-04 新增的**第 0.5 步**
   —— 碰某些成员前先查 [`docs/recon-206/pre-code-conflict-lookup.md`](../../docs/recon-206/pre-code-conflict-lookup.md)
   （**368 个成员 / 424 条**「官方 `Remarks` 与官方示例**不能同时成立**」）。
   ⇒ **本文是把那一步制度化、从静态文件升级成护士。**

### 2.3 ✅ 但两个方案**不是二选一**

★★ **方案1 的产出（一张「专家 → 工具」表）正是方案2 里护士的知识。**
⇒ **合成：方案1 的表 + 方案2 的部署。**

### 2.4 ★ MoE 类比的边界（✅ 已澄清，别再重复讨论）

| MoE 的性质 | 我们的对应物 | |
|---|---|---|
| 专家**训练出来**、路由**学出来** | 我们**提示出来**、路由**手写** | ❌ 没有训练信号兜底 ⇒ **路由质量 = 系统质量** |
| 专家在同一设备**并行** | 必须**串行**（COM 单源） | ❌ |
| 一个 token 走 **k of N** 专家 | 一个任务走一个专家，可唤醒别人 | ✅（但这是 **supervisor + 专家系统**，不是 MoE） |
| 有 **load-balance loss** 防塌缩 | 我们没有 | ❌ 缺 ⇒ **会塌缩成「一个万能专家」** |
| **没有「问同事」的概念** | ★ 用户设计的核心就是它 | ❌ MoE 里没这东西 |

⇒ ★ **更贴的类比是「医院」**：**分诊（planner）→ 专科（域专家）→ 转诊（handoff）→ 出院（sleep）**。
⇒ MoE 真正可借的是**它的两个教训**：① **路由必须可测**；② **必须防塌缩**。

## 五、已定的关键设计决策（✅）

| # | 决策 | 理由 |
|---|---|---|
| **D1** | ★★ **索引按「护士」粒度，不按「工具」粒度** | ★ 索引一行是「**该找谁**」，不是「她有什么」⇒ **护士手里的工具从 20 涨到 40，那一行一个字不变** ⇒ **拆分对 lead 是零成本**。⚠ 按工具粒度建索引，用户的担心立刻成立 |
| **D2** | **索引外化成文件**，lead 每步**读一行** | 「记不住」从失败模式里消失 |
| **D3** | ★★ **每步回读模型状态，写进进度表** | ★ 把 **O(步数) 的记忆压成 O(1)** —— 第 50 步的 lead 只需握**当前这一行 + 一次回读**，不是 49 步历史 |
| **D4** | **计划由 planner 从封闭清单里【选】，不自由写术语** | 主力已得出：**「让 AI 用规范术语」不如「让 AI 从封闭清单里选」**；且 ★ **封闭清单本仓已有**：`docs/user-feature-coverage.md` 的 **145 项**（CommandManager 粒度，11 域） |
| **D5** | **护士用阶梯，从轻到重** | 呼应「先测最朴实无华的简单方法，从轻量到重量一路试上来」 |
| **D6** | **护士的契约不止工具名** | 见 §六 |

### 5.1 ✅ 护士的四级阶梯（D5 展开）

| 级 | 护士是什么 | LLM 成本 | 能答什么 |
|---|---|---|---|
| **L0** | **查表**：`member-to-example-index` + `pre-code-conflict-lookup` + `dead-ends` | **零** | 这一步该用哪个工具、有哪些已知冲突 |
| **L1** | 表 + 在她**自己那个子集内**做 BM25 | **零** | 加「意图 → 候选工具」 |
| **L2** | **LLM 护士**（Bunny 免费、可多路取一致率） | 1 次小调用/步 | 加「意图的语义理解」 |
| **L3** | LLM 护士 + 检索回填 | 略贵 | 加「没见过的意图」 |

### 5.2 ✅ 执行循环的形状（D3 展开）

```
① 开工：把对话 → 施工计划（spec.md）        ← planner 从封闭清单【选】，不自由写
② 循环每一行：
   ②a 读该行的「需要什么工具」→ 问护士（L0/L1/L2/L3）
   ②b ★【只有 lead 碰 COM】调工具
   ②c ★★ 回读模型状态（特征树 / 体积 / 包围盒）→ 写进目标栏的「实际结果」列
   ②d 与该行的期望比 → 不符就【停】，不静默成功
③ 收工：读回全模型状态 + 出报告
```

★ **②c 是全局最不起眼、也最关键的一步。**

## 七·bis、★★★ W 曲线：把整个设计空间压成**一个参数**（2026-10-05 用户提出的统一）

### 7b.1 定义与推论

> **W = 一个 agent 一次手里拿的工具数。**
> **`p(W)` = 手里有 W 个工具时的选择准确率。**
> ★ **`W*` = 那个阈值**（准确率开始明显下降的 W）。

**用户的原话**：「热集的工具数量要定好，其实也相当于是护士手里的工具数，或者根本来说，**一个 agent 一次手里拿多少工具能不记错**」
⇒ ★★ **之前分开问的所有问题，其实都是 W：**

| 问题 | 其实是什么 |
|---|---|
| 热集多大 | `W_热` |
| 护士手里几个 | `W_护` |
| 一个 agent 拿多少能不记错 | ★ **`W*`** |
| 要几个护士 | ★ **`N = 462 / W_护`** |
| 要不要这套架构 | ★ **`462 > W*` 吗** |

### 7b.2 ★★ 要做的实验：**`p(W)` 曲线**

| W | 10 · 20 · 30 · 50 · 100 · 200 · 462 |
|---|---|
| 任务 | 官方示例的 `## Description`（厂商写的） |
| 候选 | W 个工具（真实的工具名+描述） |
| 答案 | 见 7b.5 的**代理**（成员重合）+ **小规模裁判抽检** |

**这条曲线一跑完，四件事同时定下来：**
1. ★ **架构需不需要** —— 若 `p(462) ≈ p(10)` ⇒ **不需要**，直接全给 lead
2. ★ **`W*` 在哪**（拐点）⇒ `N = 462 / W*`
3. ★ `p(W_热)` 与 `p(W_护)` ⇒ **直接算两级路由的乘积 `F3`**
4. ★ 反推**五统一命名纪律**值多少（见 7b.3）

### 7b.3 ★★★ W **不是唯一变量** —— **相似度同样是**，而这里有一个不对称

| 情形 | W | 实测/预期 |
|---|---|---|

### 7b.10 派 agent 的纪律（**什么时候才该派**）
