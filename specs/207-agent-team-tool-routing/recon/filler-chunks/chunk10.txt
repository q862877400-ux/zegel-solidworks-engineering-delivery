## 二、六条铁律

### 铁律 1 · 只做「缝合」，不做「发明」

每加一个能力，要能指认出处。四种合法来源：
| 来源 | 怎么用 | 例 |
|---|---|---|
| 官方 API 文档 | 决定接口选型与参数顺序 | Simulation 域（外部无人提供，只能照官方签名建） |
| 其它开源项目 | 直接移植 / 改写，保留来源头注释 | 建视图 ← codestack；VBScript ← pengxiaoan |
| 四家外部 MCP 项目 | 移植其能力广度，按 `provenance` 标注来源与许可 | `andrewbartels1` 的草图完全定义探针；`Slacker-LLC` 的声明式 selection |
| 本项目自身既有模式 | 沿用 `sw_part.py` / `sw_hole_features.py` 的写法与命名 | 新 `sw_xxx.py` 沿用 `_select_by_id` / `get_com_member` |

不可接受：凭印象写一个 `FeatureManager.XXX(...)` 然后「看着像对的」。

### 铁律 2 · 可以实测，但必须先关弹窗、必须有超时

验证顺序：静态签名比对（前置筛查）→ 本机实测（真跑，用 `mcp__solidworks__*` 或直接调 COM）→ 两关都过，才允许在文档里写「已验证 / 实测 / 跑通」。实测的三条安全约束：

- 先置 `ISldWorks.CommandInProgress = True` —— 未抑制的模态对话框会把会话永久挂起，这是无人值守挂起的头号原因。
- 每个 COM 调用设超时 —— COM 是 STA 且线程亲和，调用一旦开始无法强制中止；超时只救「等待」，救不了线程，超时后不要重试同一进程。
- 收尾必做 —— `CommandInProgress = False`、释放 COM 引用、关掉自己开的文档。

红线：破解相关（SolidWorks-CAD / Solidworks-Crack 类投递页、破解指南）零接触；不动注册表 / 全局环境变量 / 系统层；未经确认不 `git push` / 不建目标远端仓库 / 不发 release；不删用户数据。

### 铁律 3 · 结构按顶层白名单，不临时起目录

**结构目录**只允许这 14 个：`.github` `agents` `ai_team` `apps` `assets` `docs` `dotnet` `examples` `mcp-server` `references` `scripts` `subskills` `tests` `tools`（前 13 个上游就有，`tools` 是我们加的）。新增白名单外的顶层目录，要在本节登记它是什么、为什么放不进已有目录，再动手。

**产物 / 缓存目录**允许存在于工作树，但必须 gitignore、不入库：`.api-signatures`（签名索引）、`output`（构建产物）、`.pytest_cache`（pytest 缓存，须 ignore）。

新文件落进已有位置：能力实现进 `scripts/`，知识文档进 `references/`，测试进 `tests/`，说明与生成物进 `docs/`。上游目录树与新增模块的硬性要求见 [docs/upstream-layout.md](docs/upstream-layout.md)（对照参考，不是约束来源）。

### 铁律 4 · 签名三源互证，冲突以出厂类型库为准

本机有两套官方离线源，各有长短，都要查：`D:\AI\SW\AI Solidworks\官方文档\`（CHM 解包，权威、带说明与示例，查语义与用法）与 `C:\swapi\`（结构化 markdown，查精确签名与枚举值）。各源覆盖范围与检索入口见 [docs/sources.md](docs/sources.md)。

出厂类型库是第三套源，也是冲突时的裁决者：`FeatureFillet3` 在本机类型库里有 14 个参数，官方文档写 7 个。口径是三源互证 —— 文档、反射、CHM；冲突时以出厂类型库的反射为准。不凭记忆、不凭反射猜参数、不照抄其它项目的注释。

### 铁律 5 · 查不到就说查不到

两套源都查不到 → 写「查不到」并停下换思路，不要用相似名字蒙混。名字缺席 = 官方 API 里没有这个成员，不是「没写文档」。

### 铁律 6 · 许可红线，一次都不能越

| 许可 | 能做什么 | 义务 |
|---|---|---|
| MIT | 读、抄、改、商用 | 保留版权声明 |
| Apache-2.0 | 读、抄、改、商用 | 保留 `NOTICE`（`Slacker-LLC/solidworks-mcp` 是 `Copyright 2026 JIALE LIU`）+ 声明改动了哪些文件 |
| AGPL / GPL | 只读思想 | 不抄代码、不抄文本 |
| 无许可 / 全版权保留 | 只读思想 | 同上 |

- **单源运行**：运行时只能有一个 SolidWorks MCP —— 多个进程抢同一 COM 连接会死锁（已知事实 24），所以 MCP 选型就是运行时依赖选型：只在 MIT 那份上跑，AGPL 的 SolidPilot 只读思想。

Apache-2.0 的 NOTICE 义务跟着分发走：一旦入库，推送任何远端时都要带 `THIRD-PARTY-NOTICES.md` —— 该文件**已存在**；MIT 来源（上游与 `Eduardof0nt` / `andrewbartels1` / `vespo92`）保留各自的版权声明。完整许可判定表与来源清单见 [docs/sources.md](docs/sources.md)。

⚠ **上游改叫 `upstream`（不再叫 `origin`）是刻意的**：只有 `origin` 指向上游时，一次裸 `git push` 就会**误推上游仓库**（AGENTS.md 一贯点名的风险）。现在 `origin` 空着 ⇒ **裸 `git push` 无处可去**，从结构上消掉这个风险。

用 `git diff upstream/main --stat` 看我们相对上游的增量。**⚠ `upstream` 目前只登记了 URL、还没 fetch**（本机未联网取）⇒ `upstream/main` 这个 ref 不存在，`round_chain.ps1` 会**优雅跳过**那行统计、`report_freshness` 门禁会 **SKIP**（那是便携性守卫，不是失败）。要用对照能力就先 `git fetch upstream`。

- 三条红线（任何模式都不豁免）：删数据 / 删仓库 / 强推；对外发布；只有用户能提供的东西（凭据、业务口径）。
- ★★ **提交一律走 `python tools/commit_mine.py -m <信息文件> <路径…>`** —— 且**信息先写成文件**。
  ★ **禁止**裸 `git commit -m "<多行带引号的字符串>"`：PowerShell 会把信息里的引号/换行**当成 pathspec**（报
  `did not match any file(s) known to git`），而 **`git add` 已经成功** ⇒ 产生「**表面像提交了、实际没提交**」

  ⇒ ★ **纪律写在提交信息里没用**（我不会每轮重读它）；它必须写在本文件（每轮注入）才拦得住 ✓

## 四 · 被本规格**排除**的东西（★ 负结果，省后人重走）

### 4.1 机器代理（成员重合 argmax）—— **可用，但只在相对变化上**

* 第 3 轮我曾据「池 414 时 `p_strict` 仅 10%，而 pick-test 同池 85%」判它**不可用**。
* ★★ **第 5 轮推翻**：在**同源同批 pick** 上，`p_can_do` = **15.7%** 与 `p_strict` = **16.4%** **吻合**
  ⇒ ★ **代理无罪，那个 85% 的参照选错了**（池与呈现都不同）。
⇒ ★ **结论：代理可用于跨 W 的相对变化，但仍不可单独当绝对结论**（`spec` §8.3 逐字）。

### 4.2 ★★ `pick-test` 的「池≈2」是**误读**

* 两路合并稿各自独立判「既有 87% 是 `p(pool≈2)`」⇒ ★ **两路都错**。
* ★ 真相：`_final.json` 的 `cands` = **picker 自己的第一+第二选择**（裁判只判这两个），**不是候选池**；
  ★ 从**会话记录 `request/header.tools` 实测**：picker 的真实工具面 = **414** 个 `mcp__solidworks__*`。
⇒ ★★ **那 85.4% 是在【池 414】上测的。**

### 4.3 ★ `p_strict` 与 `p_can_do` **不是**一个东西

* `p_strict` = 「是否**逐字等于我标的那个**工具」；`p_can_do` = 「**挑的能不能干活**」。
* ★ 在本规格的某批数据上两者**数值恰好接近**（16.4% vs 15.7%），★ **但那是巧合，不是等价** ——
  ★★★ **不许因此互推**（`spec` §8.3 逐字点名这条）。

### 4.4 ★ 缓存**不可靠**（对「省 token」这条论证的影响）

| 会话 | `cacheReadTokens` | 新鲜 `inputTokens` |
|---|---|---|
| picker（10-04） | 196,608 → 291,456 | 138 → 19,372 |
| 本规格某子代理（10-05） | ★ **128** | ★★ **212,727** |

⇒ ★★ **命中时不炸；未命中时非常贵（21.2 万 token 新鲜输入）。**
⚠ 真因未隔离（前缀变了 / TTL 隔天 / `cacheWriteTokens` 恒 0 含义未知）⇒ ★ **不下因果结论**。
★ 工具定义 JSON 实测 **715,004 字节**（★ 先前引的「12.5 万字符」只是 doc 字符串，**低估 5.7 倍**）。

## 方法

铁律 2 认可的替代验证只有三种，本表属于第 1 种（静态签名比对）与第 3 种（来源可追溯）。
对每一个 COM 调用，比对三件事：

1. **承载对象** —— 这个成员挂在哪个接口上？（挂错对象比参数错更隐蔽）
2. **实参个数** —— 与官方签名的参数总数是否一致？
3. **实参类型顺序** —— 逐位对应，不允许靠位置猜语义。

判定口径：
- ✅ **通过** —— 对象、个数、类型顺序三项全对
- ❌ **不通过** —— 任一项不符
- ⚠ **未查证** —— 走容错包装或未纳入本批，不作通过与否的断言

## 批次 5 · 自动化 arity 审计（新增工具 `scripts/audit_call_arity.py`）

### 为什么需要工具

批次 2 手工审了 10 个调用点。实际规模是 **140 个调用点 / 81 个不同成员**，
且全部裹在 `_safe_member(obj, "Name", *args)` 里——这种包装让签名错误
**不抛异常、只静默无效果**，手工不可能逐个查。

### 判定口径（刻意不猜宿主接口）

调用点的 `obj` 变量名无法静态确定类型。故不问「这个接口有没有这个成员」，
而问一个**不需要知道宿主也能判定**的强信号：

> `sldworks.dll` / `cosworks.dll` 的**全部接口**里，有没有任何一个声明了
> 同名成员、且参数个数恰好等于实参个数？

- **通过** —— 有（保守，不会误报）
- **存疑** —— 同名成员存在，但所有同名成员的 arity 都对不上 ⇒ 几乎必然是错的
- **查不到** —— 全程序集无此成员名 ⇒ 必错
- **动态** —— 含 `*args` 解包，静态不可判定，**跳过并列出**（宁可漏报不误报）

签名源：`reflect-interop.ps1` 对 `sldworks.dll` 的纯元数据反射
（1032 接口 / 20,627 成员 / 712KB），产出 `iface_sldworks.txt`。
