# 057 · 死守卫的**第四种形态**：`server.py` 的 dispatch 表 vs 协议层

**Status**: Implemented（轮 138）

## 一、判法（**纯集合比对**）
```
server.py 的 45 条  ∪  batch 模块的 41 条  ==  协议层实际给出的 86 条？
```
⚠ **安全**：起 server **只发 `initialize` + `tools/list`**，一次工具都不调 ⇒ **不碰 COM**（事实 24）。

## 二、★ 结果：**45 + 41 = 86 ✓ 完全对上**
| 方向 | 结果 |
|---|---|
| `server.py` 声明了、却没进协议层 | **0** |
| 协议层有、`server.py` 里找不到声明 | **41** = ★ 正好是 `register_capabilities` 贡献的那 41 条 |
| **两条路径之间重名** | **0** |
| 每条路径**内部**重名 | **0** |

## 三、★★ 查出的第一件事：**跨路径重名此前无人检查**
```
`check_specs` 只查 **batch 路径内部**的重名
⇒ 两条注册路径之间的重名**没有任何检查** ⇒ 重名时"哪一个赢"取决于注册顺序 ⇒ **不确定**
⇒ ★ 而且**从协议层看不出来**（`tools/list` 是集合，重名会被去重）⇒ 必须在**声明层**拦
```
已补 4 条结构判据：并集 == 协议层 · 跨路径交集为空 · 各自内部无重名 · 数量守卫。

## 四、★★★ 查出的第二件事：**"顺手套上 fixture"会让判据在故障时静默跳过**
```
第一版把跨路径那条写成收 `tools` fixture
⇒ 故障注入时报 **`1 skipped`**（不是 failed）
⇒ 重名让**注册失败 ⇒ server 起不来** ⇒ fixture 拿不到响应就 `skip`
⇒ ★★ **判据"恰好在被测故障发生时静默跳过"** —— 比"没写这条判据"更糟（它看着是绿的）
⇒ 修法：该判据**只看两个声明来源**（源码 + `all_specs()`），**不碰协议层**
```
★ 与 `053`/`054` 呼应：**判据必须能被负例证伪** ——「会 skip」等效于「不能被证伪」。

## 五、★ 一次**我自己的实验做错了**（如实记）
```
第一次注入：往 batch10 塞 `solidworks_current_selection`
⇒ 以为它在 server.py 里 —— **其实它在 batch 里**（协议层那 41 条之一）
⇒ 造出的是 **batch 内部重复**，而**跨路径**判据正确地保持绿
⇒ ⚠ 且我用 `-k` **只跑一条**，把内部重复那条**排除了**
⇒ 结论：**是实验错了，不是判据错了** —— 换成真在 server.py 里的名字后，判据立刻红。
```
★ 教训：**故障注入本身也要"注对东西"**，否则会把"实验设计错"读成"判据失效"。
