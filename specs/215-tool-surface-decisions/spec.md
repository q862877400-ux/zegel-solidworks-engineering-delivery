## 二、本规格做什么（三件 + 一道门禁）

### ① a：5 个 `macro_*` 的**首句自证身份**

★★ **为什么不是"合并成一个入口"**（★ 授权里给的另一条路）：★ 那是**做不到**的，★ 依据（实测）：
  ★ 管线的入口是 `scripts/sw_macro_guard.py::generate_macro_with_guard(user_request, **model_call**, …)`
  —— ★ 它要一个 **Python callable** 作实参，★★ 而 **MCP 只传 JSON 值** ⇒
  ★ **它无法被声明成一个 `ToolSpec`** ✓
★ 另据实测：★ 那 5 个函数的**全部调用点都在同一个模块内**（`build_prompt` ← `generate_macro_with_guard`
  的两处 + `__main__`；`extract_vba_code` / `fallback_macro_for_request` 同理；
  `normalize_model_family` ← `build_prompt`；`select_template_key` ← `fallback_macro_for_request`）
  ⇒ ★★ **它们是同一条管线的内部步骤，不是五个独立能力** ✓
⇒ ★ **处置 = 首句自证身份**（★ 保留能力、★ 不删工具、★ 不动计数）✓

### ② b：3 个钣金工具**首句先说结论**

★ 只改**首句**（★ 加一句在前，★ 不动原有任何文字 —— ★ 事实 61 的"只做加法"）✓
★ `hem` 与 `one_bend` **不改**（★ 实测它们的结论**已经在窗口内**）⇒ ★ 如实记录"已达标"，
  ★ **不为了凑"五个"而改已经对的东西** ✓

### ③ c：名字冗余**规范变更提案**（★ 只出文档）

★ 落点 `docs/proposal-r1-naming-redundancy.md`：★ 讲清「DSH 已用 `mcp__<server>__` 消歧」这个前提、
  ★ 改名会打断哪些东西（`capabilities.yaml` 的 `mcp_tools` / `all_specs()` / 文档 / 测试 / R1 门禁）、
  ★ **三种可选口径**（保留现状 / 去前缀 / 新增加别名层）与**各自代价**，★ **不替业主拍板改规范** ✓

### ④ 门禁化：`scripts/check_lean_first_line_caveat.py`（★ 硬门禁）

★★ 判据（★ **判据是量出来的，不是拍的**）：
  ★ 若某 spec 的 `doc` 含 **强自指标记**（`仍不可用` / `NOT USABLE`）⇒ ★ **它必须也出现在 lean 首句里** ✓
★ **为什么只收这两个标记**（★ 实测数据在这里，★ 这是本规格最要紧的一次取舍）：
  | 标记集 | 命中 | 真阳性 | 结论 |
  |---|---|---|---|
  | `不可用`（宽） | 12 | 3 | ✗ 9 条假阳性 |
  | `建不出` | 7 | **0** | ✗ 全是"某条路建不出"的历史叙述 |
  | ★★ `仍不可用` + `NOT USABLE` | ★ **3** | ★ **3** | ★★ **零假阳性 ⇒ 可以做成无豁免的硬门禁** ✓ |
★ 另收一条**同理可判**的：★ 若 spec 的 `doc` 提到 `generate_macro_with_guard`（★ 即"我是那条管线的一步"）
  ⇒ ★ 首句必须自证 `内部件` ✓（★ 5 条，★ 同样零假阳性）✓
