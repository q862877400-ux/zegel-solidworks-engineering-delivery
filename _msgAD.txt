fix(coverage): 把「触及」拆成「编目录」与「真调用」两列 —— 之前的数字被高估了

## ⚑ 本轮最重要的发现：我之前报的覆盖数字是**高估**的
覆盖表的归因规则把**登记表里的名字**也算作「触及」。于是
「族触及率 100%」是**靠把名字列进登记表达成的**。

量化一下（对 `scripts/` + `subskills/` 逐行扫）：

| | 数量 |
|---|---|
| 代码里**真的调用/点调用**的成员名 | 886 |
| 登记表里**列出来**的名字 | 7690 |
| **只在登记表、从未被调用** | 7031 |

按接口族算（16,615 个成员）：

| 指标 | 编目录 | **真调用** |
|---|---|---|
| 成员覆盖 | 12,870（77%） | **2,636（16%）** |
| 族覆盖 100% | 337 / 701 | **18 / 701** |
| 族覆盖 ≥ 50% | 534 / 701 | **68 / 701** |
| 触及率中位数 | 95% | 42% |

⇒ **合并汇报这两个数字就是误导。**
「编目录 77%」证明的是「这份 API 清单做完了」，
**不是「这些 API 都能用了」**。

## 改了什么
1. **生成器**：`repo_members()` 从返回一个集合改成返回两个
   （`called` / `catalogued`），逐族算 `pct` 与 `used_pct` 两个指标
2. **表头**：写明两列含义不同、不可合并，并给出当前实测值
3. **SKILL.md / harvest-report.md / gap-analysis.md**：三份文档的判据表
   全部换成双指标版本

## 这不是措辞问题
早先我反复说「无整族缺席 ≠ 全覆盖」，但**表里那个 100% 本身就是靠列名字达成的**，
我却拿它当覆盖率汇报。拆成两列后，真实情况是：
**API 清单基本做完（77%），实际封装 16%。**
这是两件很不一样的事，不该挤在一个数字里。
