> **把工具通道换成「可调用骨架」不会让选择变差**（两轮都比全量 schema 略好，但**不显著**），

## 一 · ★★ 三条已经能定的结论

| # | 结论 | 依据 |
|---|---|---|
| **1** | ★★★ **不要把工具搬进 code 模式** | E vs A **两次重复都显著更差**（p=0.0243 / 0.0022，`p_yes` −7.0pp / −10.1pp）；★ 且弃权 **24 / 29** 题（它在写代码探索工具列表，而不是选工具） |
| **2** | ★★ **「骨架通道」可以放心替换全量 schema** | B/C/D 的 `p_yes` **两轮都 ≥ A**（+4.5/+4.5/+4.0 与 +3.0/+2.0/+4.5），★ **两轮都没有一方向变差**；单轮不显著 ⇒ ★ 只能说**「不差」**，**不能主张「更准」** |
| **3** | ★★ **系统提示词里的「目录」那一半可以不要** | B vs C **两轮都 p≈1.0**；★ 去掉它把 86,232 → **51,729 token（0.19×）** |

★ **一处对我方假设的更正**：我原以为「**保留参数**」是准确率的来源（旧研究只证了删参数会崩）⇒
★ **两轮都没有证据支持**：D（目录无参数）与 B 无差别（p=0.82 / 0.61）。

## 二 · ★★★ 本轮最有分量的新读数：**F 臂（纯文本索引）与 SC-9 的自检失败**

**F 是什么**：忠实复现旧研究（207）的 index 臂 —— **没有 tools 通道**，系统提示词里只给一份
「工具名 + 一句≤30字用途」的清单，模型**用文字回答**工具名。

| 量 | F（本轮实测） | 旧研究（207）index 臂 |
|---|---|---|
| 呈现 | 名 + ≤30 字用途，**无通道** | 名 + ≤16 字用途，**无通道** |
| 工具数 | **731** | 414 |
| 首轮 token | ★ **16,490** | （旧研究报 5,114 token 的极简索引） |
| 准确率 | ★ **`p_yes` 0.6784** | ★ **22.9%** |

⇒ ★★★ **我复现不出那 22.9%**。在**同一套题、同一套判据、同一个模型**下，
「只给名字与一句用途」拿到的是 **0.678**，而不是 0.23。

★★ **⇒ 规格 208 的 SC-9（方法学自检）不成立**，必须据此限定与 207 的可比性：
* 207 的 22.9% 与我的 0.678 **不是同一个实验**（题源不同、工具集不同、判据由不同主体给）。
* ★ **两种解释都还开着**：① 207 那次的分母是 `p_strict`（逐字等于代理答案）而不是「能不能干活」；
  ② 207 的题源是**官方示例的 API 用法描述**（它自己后来也判为病根）。
⇒ ★★ **结论：不能拿 207 的 22.9% 当「压缩会崩」的既定事实**，那条需要被重测。

## 五 · 建议（★ 等业主判「合格」后才落地）

1. ★★★ **最省的可用配置是 C**：`mode: lean` + `leanCatalog: false` ⇒ **0.19× token、不差**，**不需要 PTC runtime**。
2. ★★ **若愿意再赌一步，可以测 F 形态**（纯文本索引、无 tools 通道）—— 0.060×，本轮拿到 0.678，**但缺 r1 配对**，先补一次重复再说。
3. ★★★ **明确不要用 code 模式承载工具选择**（两次都显著更差）。
4. ★★ **顺手修命名卫生**：524 个 `mcp__solidworks__*` 里 465 个重复前缀 ⇒ 编名率 1–2.5%。
