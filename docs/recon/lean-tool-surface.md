# Lean 工具面：把 PTC 式工具加载嫁接到原生模式（规格 208 · 交业主裁定）

> ★ **一句话结论**：**把工具通道换成「可调用骨架」后，准确率与全量 JSON schema 持平（+4.5pp，不显著），
> 而每轮 token 只剩 0.19～0.31×**；★ 而 **PTC 的 code 模式反而显著更差（−7.0pp，p=0.024）**。
> ⚠ 不含行号。★ 每个数带口径。★ **未改生产环境**。

---

## 〇 · 三个可执行的结论

| # | 结论 | 依据 |
|---|---|---|
| **1** | ★★ **「骨架通道」值得上** —— 同样的选择准确率，**token 降到 1/5** | C 条件：**51,729 token（0.189×）** · `p_yes` **0.6985** ≥ A 的 0.6533 |
| **2** | ★★ **系统提示词里的「目录」那一半可以不要** | B（带目录 86,232 tok）与 C（不带目录 51,729 tok）**准确率逐字相同**（0.6985）；McNemar **p=1.000** |
| **3** | ★★★ **不要把工具塞进 code 模式** —— 它显著更差 | E 条件 `p_yes` **0.5829** vs A 0.6533 ⇒ **−7.0pp**，**McNemar p=0.0243（显著）**；★ 且 **24 题直接弃权**（去写代码探索工具列表而不是选工具） |

★ **对我方先前假设的两处更正**：
* 我原以为「**保留参数**能救回准确率」（旧研究只证了「删掉参数会崩」）⇒ ★ **本轮没有证据支持**：D（目录无参数）0.6935 vs B（目录带参数）0.6985，**差 0.5pp，p=1.000**。
  ★ 真因是我原先把「删参数」的代价**记在了目录上** —— 而**骨架通道里根本不含语义，准确率却没掉**。
* 我原以为 **PTC 的加载方式**是主要收益来源 ⇒ ★ **PTC 的 code 模式是本轮唯一的显著负结果**。

## 二 · 五条件定义（一次定义死）

| 条件 | 工具通道 | 系统提示词 | 能否原生调用 | 依赖 PTC runtime |

## 五 · ★ 一条独立于准确率的读数：命名不一致会被模型「揉」

* SolidWorks 面 **524** 个里，**465 个**把前缀重复了一遍（`mcp__solidworks__solidworks_*`）、**59 个没有**。
* ★ 实测**编造名字**：A 2\199 · B 1\199 · C 5\199 · D 2\199 · E 3\199 ⇒ **1.0%～2.5%**。
* ★ 典型编造：`mcp__solidworks__solidworks_add_sketch_constraint`（真名是 `mcp__solidworks__add_sketch_constraint`）、
  `solidworks__solidworks_sketch_trim`（少了 `mcp__`）、`create_pattern`（少了整个前缀）。
⇒ ★★ **这是命名卫生问题，不是加载方式问题** —— 但它污染了 `no` 的一小部分。

## 八 · 建议（★ 等业主判「合格」后才落地）

1. ★★★ **日常 preset 用 C 形态**：`mode: lean` + `leanCatalog: false` ⇒ **0.189× token、准确率不降**。
2. ★★ **把 `mode: lean` 做成生产可用**：★ 它**不需要挂 PTC runtime** ⇒ 改一个配置项即可，零新增依赖。
3. ★ **不要往 code 模式搬工具**（E 显著更差，且弃权率 12%）。
4. ★★ **顺手修命名卫生**：524 个 `mcp__solidworks__*` 里 465 个重复前缀 ⇒ 统一后应能减少那 1–2.5% 的编名。
