# C1 · 多路一致率（Bunny 两路 × 788 个官方成员页）

> **这一份回答**：让两个**独立的 Bunny 抄录路**去抄同一批 788 个官方成员页的四个字段，
> 它们**互相**多一致、**各自**与标准答案多一致，以及**裁判能不能推翻这些数**。
>
> **为什么这件事只有我们能做**：本项目本轮已实测 —— Bunny **每一路都自称「已逐字校验」**，
> 而引文逐字回查抓出 **11/7360 = 0.15%** 是编造。⇒ **同模型自证不算证据**，必须有闸。
> 本文件就是那道闸的**量化结果**。
>
> **来源与口径**
> - **源**：`C:\swapi\types\` 的 `IView`（461）+ `IDrawingDoc`（274）+ `ISheet`（53）= **788** 个成员页
>   （不含 `_overview.md`）。
> - **两路**：Bunny（`opencode-zen` / `space-bunny-free`）**同一批 788 页、两套不同措辞的提示词**各跑一遍
>   （A 路 60 箱、B 路 60 箱，**各 788 行**）。★ 提示词措辞不同是刻意的 —— 降低两路犯同一个错的相关性。
> - **标准答案**：`truth.json`，由**本仓解析器**从页面算出（不是人核的，**它自己也有错 —— 见 §四**）。
> - **三个裁判**（**路由不同、看的方向不同**）：
>   V1 = `deepseek-official` / `deepseek-flash`（审计者）· V2 = Bunny（对抗者）· V3 = Bunny（复算者）。
>
> ⚠ **本文件不含行号**。

### 2.1 ★★ V1 与 V3 一致指出的**我的错**（这是本次门禁最大的产出）

| 我原来的说法 | 裁判指出 | 真值 |
|---|---|---|
| 「A vs B **原始**一致 3144/3152 = 99.75%」 | **「原始」不成立** —— 3144 要先剥反引号 | 原始 = **3000/3152 = 95.18%** |
| 「A 对标准答案 **100%**」（无条件） | 依赖**两个未声明前提**：剥反引号 + `obsolete` 取 loose | 取 strict 则 **786/788** |
| 「归一化错别字即 100%」 | 须**同时**剥反引号；只归一错别字得 **3008/3152** | 见 §一 L1/L2 |

⇒ ★★ **教训（已写进 `docs/recon/README.md` 的纪律）**：
**报告任何一个"一致率"时，必须写明归一化层级与口径；否则同一个数据能报出差 4.5 个百分点的两个数。**

### 2.2 V1 报出的判据缺陷（**8 条，逐条留档**）

1. obsolete 给了 strict/loose 两栏却没说用哪栏；二者只差 2 条（两条 CompoundNote），而「100%」只在取 loose 时成立，取 strict 则 A=3150/3152。
2. strict 只认行首带句点的「Obsolete.」，于是「Obsolete for documents…2016 and later.」这类版本限定式废弃被漏判；二元值也表达不了这第三态。
3. pointer 题面判据（## Returns 含 in-process, unmanaged C++）与标准答案不同：truth 用不分大小写的「unmanaged C++」（我复算 51/51 命中），字面判据只 47，漏 4 条。
4. 漏的 4 条里有 1 条是官方原文自己拼错（IDrawingDoc/IGetPenInfo.md 第17行「in-porcess」），另 3 条是「In-process」大写开头。字面字符串判据对源文拼误与大小写零容忍，必然漏。
5. zero 四值不是同一根轴：空括号/有形参判方法元数，「是（无括号）」判成员种类（属性），「查不到」判页面缺正文；实测 method 只出前两者、property 只出后两者。
6. zero 不区分 {get;}（12 条）与 {get; set;}（33 条），两者都归「是（无括号）」⇒ 只读/可写信息丢失；这也正是把 {get;} 误读成「空括号」的成因。
7. signature 写「签名原文」，但源文是 **Signature**: `…`，判据未定义代码跨度反引号算不算原文；仅此一点就占 A/B 原始不一致 152 格中的 144 格（A 带 130、B 带 92、truth 带 0）。
8. 四条判据混了两种任务：signature 是逐字抄录，obsolete/pointer/zero 是分类判断，却用同一套精确比对计分 ⇒ 格式噪声与语义错同权，这也是 95.18% 被写成 99.75% 的根源。

### 2.3 V2 报出的 `truth.json` 3 处错（**我的解析器错，不是 agent 错**）

1. `IDrawingDoc/CreateCompoundNote.md` 的 `obsolete_strict`：标准答案说 `false`，**实际应为** `true —— 页头行首确实是 Obsolete；strict 漏判，loose=true 才是对的`
   依据逐字：`Obsolete for documents created in SOLIDWORKS 2016 and later. Superseded by [[ISketchBlockDefinition]] and [[IS`
2. `IDrawingDoc/ICreateCompoundNote.md` 的 `obsolete_strict`：标准答案说 `false`，**实际应为** `true —— 同一处漏判，同一形态`
   依据逐字：`Obsolete for documents created in SOLIDWORKS 2016 and later. Creates and returns a compound note.`
3. `IDrawingDoc/IGetPenInfo.md` 的 `pointer`：标准答案说 `true`，**实际应为** `按你声明的判据应为 false：官方页把 in-process 拼成了 in-porcess，字面量不成立。实质语义仍是 true（该成员确是 in-process 方法），但这个 true 不是由声明的判据算出来的`
   依据逐字：`- in-porcess, unmanaged C++: Pointer to an array of longs (see **Remarks**)`

★ 特别值得注意第 3 条：`IDrawingDoc/IGetPenInfo.md` 的 `pointer` ——
官方**自己把 `in-process` 拼成了 `in-porcess`** ⇒ **按我声明的字面判据算不出 `true`**，
而我的解析器「宽容」地认了笔误。⇒ **判据与标准答案口径不一致这一件事，在本轮出现了 3 次**
（反引号 / obsolete 两口径 / 笔误）。

### 2.4 V3 报出的方法学问题（**8 条**）

1. 错别字当不一致会把一致率虚低：8 处 形号/形参 全是 B 的抄写噪声，与能力无关；归一后 B 对 truth 也是 100%，raw 与归一两档应并报。
2. 分母 3152（788x4）把四栏等权：两栏布尔、signature 长串一字错即整格错、zero 4 态；signature 的字符敏感度主导曲线，按行数 788 更贴近抄对没有。
3. signature 栏实际在测“抄没抄 markdown 反引号”而非“签名对不对”：truth 0 行带 、A 130、B 92，144 处不一致全由此生，须先规范化再判。
4. obsolete 栏取 strict 还是 loose 从未声明。取 loose 才 100%、取 strict 是 99.94%，这 2 格是真实分歧被口径选择藏起来，不是抄对了。口径必须在报告里写死。
5. zero 栏有“查不到”未定义态 3 行（IDrawingDoc/Sheet.md、ISheet/TableAnchor.md、IView/RootDrawingComponent2.md），进了分母却不构成可判对错的二值项。
6. 整体 replace(号->参) 不安全：号 在 459 行是合法的 括号（414 空括号 + 45 无括号），只有 8 行是错字。必须限定 形号->形参。我验过两种写法在本数据上结果相同，但只有后者可靠。
7. 一致率不等于正确率：A 对 B 高只说明两路互相像，两路同型抄错同一处在此度量下仍拿满分。要判对错只能用 truth，而 truth 本身也是解析器产物、未经人工复核。
8. 144 处不一致全部落在两个长尾字段（signature 644/788 与 zero 780/788），obsolete 与 pointer 两栏均 788/788 全同；逐栏分开报比报一个总数更能定位问题。

## 三、这个数能怎么用（**给主线的三个用法**）

1. **`signature` 栏在 L1 层两路都是 100%** ⇒ Bunny 抄官方签名**逐字可信**（但这要求先做反引号归一）。
2. **两路在 L2 层 788/788 完全一致** ⇒ **两路互洽性 100%**，即「同一模型的两次独立跑不会给出互相冲突的答案」。
   ★ 注意这**不等于正确**：V2 说它推翻不了任何一条"一致"，**但两路可能一起错**（那要标准的第三方来源才能发现，见 §四）。
3. **单路错误率**：B 路在 L1 层 8 处错（**全是同一个错别字**）⇒
   **一个重复的抄写模式就能占掉全部错误** ⇒ 度量里"归一化错别字"这一档**必须单列**。

## 四、⚠ 本文件**不能**说明的事（边界）

* ⚠ **一致 ≠ 正确**：两路互洽 100% **只**说明这两次跑不冲突。
  真正判"对不对"用的是 `truth.json`，**而它自己已知有 3 处错**（§2.3）⇒ **三者都不是金标准**。
* ⚠ **没有第三方独立来源**：本件的"标准答案"仍出自**同一个仓库的解析器**。
  要真正独立，需要官方 CHM 或另一套提取器 —— **本轮没做**。
* ⚠ **3 行不可判**：`IDrawingDoc/Sheet.md` · `ISheet/TableAnchor.md` · `IView/RootDrawingComponent2.md`
  是空壳页（无签名 / 无 Returns）⇒ 它们的 `zero="查不到"` 进了分母却不构成可判对错项。
* ⚠ **只测了 3 个接口 788 页**（占全量 11557 页的 6.8%）⇒ 不能外推到全库。
* ⚠ **DeepSeek 那 19 箱 254 行是"当选手"的校准读数**（1 处错 / 99.61%），
  **不作为本件的产出**（我一开始误把它当产出方，已停；见 `verifiers.md` 顶部留档）。
