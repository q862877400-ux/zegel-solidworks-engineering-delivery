## 二、现状为什么这样（★ 不是疏忽，是**选过的**）

★★ `docs/union-conventions.md` 规则 1 那一节**逐字写着**选择理由：

> **为什么统一到 `solidworks_`**：本仓库上游已有 45 个工具用这个前缀（`solidworks_connect`、
> `solidworks_create_basic_part`）；`cadstudio_*` 保留给**无 SolidWorks 的 headless 路线**，
> 两者语义不同，不混用。

★ 拆开看，这个选择担了**三件事**：
1. **缝合一事一议**：本仓是**四家外部项目 + 上游**缝出来的（铁律 1）——
   ★ 没有统一前缀，就会出现 `sw_*`（Eduardof0nt 风格）/无前缀/`vba_*`（vespo92 风格）★ **五花八门** ✓
2. **区分两条后端路线**：`solidworks_*` = 真机 COM；`cadstudio_*` = 无 SolidWorks 的 headless
   ⇒ ★ 前缀在这里**是一份语义承诺**（★ 模型据此能判断"这个工具要不要真机"）✓
3. **承接上游 45 个既有工具**：★ 那 45 个我们**一行没改**（AGENTS.md §〇 逐字）⇒
   ★ 前缀是**继承来的既有事实**，不是新加的装饰 ✓

## 三、三个选项与各自代价

### 选项 A · **保留现状**（★ 建议）

★ **代价**：★ 显示层继续有 `mcp__solidworks__solidworks_*` 这层重复 ✓
★ **收益**：★ ① 口径层三件事（§二）全部保住；★ ② **零改动面、零回归风险**；
★ ③ 与上游 `server.py` 那 45 个工具保持一致（★ 那 45 个**不该**因我们的命名偏好被改）✓

### 选项 B · **去前缀**（`extrude_boss` 之类）

★ **代价（★ 实测，不是估）**：
- F8：★ 全仓 `.py` 里有 **2273 处** `"solidworks_*"` **字面量**，★ 分布在 **465 个文件** ✓
- F9：★ `capabilities.yaml` 里另有 **395** 处 ✓
- F10：★ 要**同步改**：`register_capabilities` 的 `name=` 与**注入名**· `docs/union-conventions.md`
  **规则 1** 与 `scripts/check_union_conventions.py` 的 R1 正则· 大量**测试**（含"钉死工具数/名字"的那几类）·
  `docs/*.md` 与 `capabilities.yaml` 的 `mcp_tools` ✓
- F11：★★ **破坏既有引用**：★ 凡按名调用过这些工具的人（提示词、脚本、别的 MCP 客户端配置）
  ★ **全部失效** —— ★ 而本仓**没有**版本化的工具名别名机制 ⇒ ★ **无平滑迁移路径** ✓
- ★ **而且它并没有真的消掉冗余**：★ `cadstudio_*` 那 13 个**必须留前缀**（F7 的语义承诺）
  ⇒ ★ 结果会是"**459 个没前缀 + 13 个有前缀**"的**不一致**，★ 比现状更难解释 ✗

### 选项 C · **保留名字 + 加别名层**（★ 只在显示层去重）

★ 做法：★ 工具名**不动**；★ 由**客户端/宿主**在展示时去掉与服务器同名的冗余前缀
（★ 即 `mcp__solidworks__solidworks_x` → 显示为 `solidworks_x`）✓
★ **代价**：★ 改动落在**宿主/客户端**（★ **不在本仓库**）⇒ ★ 本仓**零改动** ✓
★ **收益**：★ 消掉显示层冗余，★ 保住口径层三件事 ✓
⚠ **前提**：★ 这需要宿主支持"按服务器名去重复前缀"的展示规则 —— ★ **本仓管不到这一层**，
★ 故本提案只把它记为**可选的最小代价路径** ✓
