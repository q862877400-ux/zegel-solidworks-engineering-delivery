# SolidWorks 自动化项目 · 请高级 AI 裁六件大事

你看不到我们的文件，所以本文不引用文件名与路径。前面几轮你给的技术性建议我们已采纳并在执行，**那些不再问**。这一份只问**方向与框架**——是我自己不该拍、也拍不了的六件事。

## 背景（够你判断用，不多写）

一个自建的 SolidWorks 自动化仓库：把官方 API 封成 **448 个可被 AI 调用的工具**，每条能力登记真机证据与验证等级（现 126 条：110 条真机验过、14 条只有代码、2 条明确不做）。规模：入库文件 6022、能力模块 176、测试文件 289、真机探针脚本 590、工作项 157 个、自动门禁 33 道。全部真机结论来自**一台机器、一个 SolidWorks 版本、一个绑定后端**。

它的人手是**一个人 + AI**，长期以"轮"为单位推进（现有 157 个工作项）。它的立身之本是判据一律用**回读**（调完再读状态），不看被调成员的返回值。

## 一、这个项目的终局是哪一种？四个目标从没排过优先级

项目自己的任务陈述里并列着四个目标：**并入四家外部开源项目的广度**、**攻三个没人做过的空白域**、**做到五统一的正规军**、**运行期单源交付**。它们平级并列，**从未被裁过谁主谁次**；而实际上所有资源分配都默认了"广度优先"（448 个工具、157 个工作项都在服务它）。

**我要你裁**：这四个里哪个是主目标？因为"全覆盖式的能力库"和"能做成一件事的智能体底座"是两种不同的架构——前者优化覆盖，后者优化任务闭环，两者的取舍在资源紧张时会走向完全不同的路。

## 二、"能力数量"这条路已经到顶了，下一个交付形态是什么？

按用户视角清点的功能覆盖率到了 119/145，我们三路独立核算的结论是：**这条路线已到天花板，再往上只能新增真实现**，靠"刷"只会记假账。同时，我们**没有任何任务级的成败数据**——没有一次"让智能体用这套工具完成一个真实任务"的度量。

**我要你裁**：下一步该往哪个形态投？是把现有能力打磨成任务闭环，是继续补新能力域（还剩两个空白域没做），还是把重心移到"让外部能用"（稳定接口、文档、发布）？我倾向第一种，但说不清它的收益要多久才显现，而这正是我不敢拍的。

## 三、验证的可扩展性——这是架构问题，不是流程问题

我们的验证纪律本身是好的（判据用回读、"选不上"与"选了没用"分开记）。但**每条能力的真机验证都是人手设计的一次性探针**（590 个脚本），能力从 110 涨到 448 时，验证成本线性增长、质量参差——现在已经查出 7 条能力指向根本不存在的工具、14 条"并进来从未运行"、197 个工具没有任何能力条目。

**我要你裁**：要不要把验证改成**声明式 + 自动合成**（从工具自己的声明自动生成探针与判据），代价是什么？如果走这条，**哪些判据注定不能自动生成**？我的猜测是"几何正确性"和"前置可达性"两类不能，但我想要你的判断。

## 四、治理形态：按"单人+AI"治理，还是按"团队+流水线"治理？

仓库里现在**同时存在两套治理痕迹**，且都不完整：一套是单人长跑式的（一张 559 条的实测结论表、157 个工作项、一份每轮自动注入的常驻指令），一套是团队流水线式的（任务板、角色分工、多轮独立评审）。两套都在用，两套都在膨胀——常驻指令已经被那张事实表占到七成以上，靠不断往外部文件搬迁来维持。

**我要你裁**：这个项目该按哪种规模治理？因为它决定"膨胀"要不要当成问题治、要不要引入更重的流程、以及我该不该继续把每一条实测结论都写进那张表。

## 五、与上游、与那四家外部项目的长期关系是什么？

项目最初是"补强上游 fork"，中途转向"自建仓库 + 引用各家"，后来又回过头补上游的 API 缺口。现在仓库里既有上游的代码（原样未改），也有从四家移植的能力，许可证义务已按最严的那份处理（带第三方声明）。

**我要你裁**：这个仓库与上游、与那四家**长期**是什么关系——继续追上游、保持可 rebase？还是彻底独立、只在来源表里引用它们？这决定构建与发布策略，也决定我以后要不要花时间做与上游的对差。

## 六、风险集中度与"成功"的判据

所有真机结论都来自**一个版本、一个后端**。而我们已经在"换后端"上吃过一次判断错误的亏：把一条**绑定层**的限制记成了**平台**的限制，还据此断言"另外两种后端也不行"，而那条断言**没有任何实测证据**。

**我要你裁两件**：一是要不要、以及何时把验证面扩到别的版本与后端；二是**这个项目成功的判据应该是什么**（给我一句话），以及在**没有真实用户**的情况下，怎么近似它。
