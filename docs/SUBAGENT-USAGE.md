# 怎么用「便宜模型助手」省 Lead 的输出 token（★ 基于 2026-10-03 的实测）

> ★ 本文回答一个问题：**想让一个便宜、大上下文（256k）的助手替我干活，好省我的输出 token —— 该怎么用它？**
> ★ 全部结论都来自本会话的**实测**，★ 而不是推测。

---

## 〇、先记住三条**硬约束**（★ 它们决定"能怎么用"）

| # | 约束 | 实测证据 |
|---|---|---|
| ① | ★ **模型不能按次指定** —— 团队成员/子智能体的模型由 **role → 固定路由** 决定（`worker` / `artist` / `reviewer` / `researcher` / `writer`），★ **没有 per-spawn 的模型参数** | 本会话 `list_agents` 显示全部成员都挂在同一个模型上 |
| ② | ★★ **团队成员名额上限 = 8**，★ 而**没有"移除成员"的工具**（★ `interrupt_agent` 只中断、不移除）⇒ ★ **满了就只能等** | `spawn_teammate` 报 `Team member limit 8 reached` |
| ③ | ★★ **SolidWorks COM 是单源会话**（★ 本仓事实 **24**：★ 多个进程抢同一 COM 连接**会死锁**） | 写进 `AGENTS.md` 的"单源交付" |

⇒ ★ **故本机可用的派活通道是 `subagent`**（★ 普通子智能体、**不占团队成员名额**）✓
  ★ 而★ `verify_rollout` 在本机**不可用**（★ `no adapter registered for provider "stepfun"`）⚠

---

## 一、★ 什么活该派 / 什么活**绝不能**派

### 1.1 ★ 值得派（★ 高省、低风险）

| 类型 | 例子（★ 本会话实测过的） | 为什么省 |
|---|---|---|
| ★★ **批量读取 → 结构化清单** | 「读这 3 个官方页 + 1 个例子 ⇒ 出**签名/参数/Remarks/调用序**四节」 | ★ 我原本要**自己读完再打字**；★ 那**全是输出 token** |
| ★ **穷举搜索** | 「全库找所有提到 `X` 的文件，★ 只回路径列表」 | ★ grep 结果可能几百行，★ **不必进我的上下文** |
| ★ **机械改写 / 格式搬运** | 「把这 N 个文件的头部改成统一模板」 | ★ 纯体力活 |
| ★ **初稿** | 「按这个大纲写一份文档初稿」 | ★ 我只改不写 |
| ★★ **独立复核我的结论** | 「拿官方原文**逐条比**这段结论，★ 指出任何编造」 | ★ 换个视角，★ 而**判据是我给的** |

### 1.2 ★★ **绝不能**派（★ 派了会亏）

| 类型 | 为什么 |
|---|---|
| ★★★ **真机 / SolidWorks 操作** | ★ **会死锁**（★ 事实 24）—— ★ 那是**硬约束**，★ 不是"效率问题" |
| ★★ **判据的设计**（★ 什么算"建成"、门禁该查什么） | ★ 判据是**我的**职责；★ 它给的判据**往往看着合理而漏掉要害** |
| ★ **跨轮记忆 / 上下文连贯的事** | ★ 它的 256k 是**一次性的**；★ 而我的纪律（事实表 / 台账）是**跨轮的** |
| ★ **写 `capabilities.yaml` / 台账 / `known-facts.md`** | ★ 那些要**逐条对齐本仓格式与事实编号**；★ 它不熟 |
| ★ **要"看真机结果再决定下一步"的活** | ★ 那是**探针的迭代**，★ 必须我亲自做 |

## 二、★★★ 最省的调用形态（★ 这一节是核心）

> ★ **关键洞察**：★ 它的**输出**不占我的输出 ✓ ——
> ★★ 但★ **它回给我的东西要进我的上下文**（★ 那是**输入** token，★ 一样烧预算）⚠
> ⇒ ★★★ **故省 token 的要害不是"让它多干"，★ 而是"让它少回"** ✓

### 2.1 ★ 三条做法（★ 按省 token 效果排序）

```
① ★★★ **让它把长产物写进文件，★ 只回"路径 + 3 行摘要"**
   ⇒ ★ 它的长输出**完全不进我的上下文**；★ 我要用时**按需 read 那一段**（★ 甚至只读某几行）
   ★ 实测（事实 483）：★ 那次它是**回在正文里**的 —— ★ 而**那次回报很长** ⚠
     ⇒ ★ 若改成写文件 + 短回执，★ 我能省掉那一大段

② ★★ **给它"定长输出"的格式约束**
   例：「★ 只输出一张表，★ 四列、每格不超过 40 字、★ 不要解释」
   ⇒ ★ 避免它写散文（★ 散文最难压缩）

③ ★ **要求它**带出处行号****
   例：「★ 每条结论后面标 `(文件名 · L行号)`」
   ⇒ ★★ 那让**我的验收变成"抽查几行"** ★ 而不是**通读** ✓
```

### 2.2 ★ 一个可直接复制的模板

```
【任务】读 <这几个官方文件>，产出 <一份四节的清单>。
【交付方式】★ **写进文件** `<目标路径>`，★ 然后**只回我三行**：
   ① 文件路径  ② 每节的关键内容各一句  ③ 你拿不准的地方
【硬要求】
   · ★ 每条结论后面标出处 `(文件名 · ## 小节)` 或行号
   · ★ 官方**没写**的写「官方没写」—— ★ **禁止推测、禁止补全**
   · ★ 不许改任何已有文件 · 不许跑真机 · 不许跑 pytest
【我会怎么验】★ 我会拿官方原文**抽查若干条**；★ 发现一处编造即整份作废。
```

## 三、★★ 验收怎么做得"便宜又不漏"（★ 否则省下的 token 会以返工形式还回去）

★ **核心原则**：★ **把验收也做成"静态比对"**（★ 本仓那条纪律：★ *把验证责任转移到静态比对*）

```
① ★★ **机器可核的先机器核**：★ 写 3~10 行脚本，拿官方原文去比它给的数值/行号
   （★ 本会话就是这么核的：★ 数签名逗号数、grep 那 7 行、统计 mark 值）
② ★ **抽样核"不可机器核"的部分**：★ 抽 2~3 条**最关键的**结论，★ 回原文看
③ ★★ **专挑"最容易编造"的地方问它**：
   · ★ 「这个数值官方写在哪一页哪一节？」（★ 编造者往往答不上小节的准确名字）
   · ★ 「官方**没写**的是什么？」（★ 编造者往往把没写的也"补全"了）⚠
   · ★ 「有没有你没读到、但被提到过的成员？」（★ 看它会不会漏引）
④ ★ **一次不合格就别再派同一类活**（★ 用户的判断标准：★ 若它**额外增加负担**就停用）
```

★ 本会话的**实测结论**（事实 483）：★ 派了一次「读官方页 → 出调用序清单」，
  ★ **四项全对、零编造**、★ **还答出了我台账上挂着的待办** ⇒ ★ **净收益为正** ✓
  ★ 而代价是**我逐条核了一遍** —— ★ 但★ **核的成本 ≪ 我自己读完再打字** ✓

---

## 四、★ 什么活**不值得**走这条路（★ 因为核的成本 > 省下的）

```
· ★ **一句话就说得清的事**（★ 派活本身的指令 token ≈ 我自己答）
· ★ **我本来就只输出几行的事**（★ 没有可省的输出）
· ★ **我已经知道答案、只是懒得打**（★ 那派人等于**多一轮往返**）
· ★ **要反复来回才能收敛的事**（★ 每轮回执都进我的上下文）⚠
```

---

## 五、★ 一句话总结

> ★ **让它"读得多、写得多、回得少"；★ 而判据与真机永远留在 Lead 这边。**
>
> ```
> ★ 派：批量读 + 穷举搜 + 机械改 + 初稿 + 独立复核
> ★ 不派：真机（会死锁）· 判据设计 · 跨轮记忆 · 本仓格式体
> ★ 形态：写文件 + 短回执 + 带出处行号 + 定长输出
> ★ 验收：机器可核的先脚本核 → 抽 2~3 条回原文 → 专挑"最容易编造"处问
> ★ 止损：一次不合格就不再派同类
> ```
