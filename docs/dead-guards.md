# 死守卫的**第二种形态**：定义了却从没被调用的函数

> 来源：`tools/probe_uncalled_helpers.py` + `tests/test_no_uncalled_helpers.py`
> （2026-10-01 轮 136，Spec Kit `055`）

## 一、为什么扫这个形态
`053`/`054` 扫的是**常量**形态的死守卫 —— 规则 2 的两半
（`_LEN_SUFFIX` / `_ANGLE_SUFFIX`）**都定义了却没人用**。
★ 本轮扫**函数**形态：**门禁/工具模块里定义了却全仓库没人调的辅助函数**。

⚠ 已知事实 61 的定则④就说过这一类：
> 「写了一个好用的工具函数，就要在**所有**同类场合用它，别只用在门禁里」

## 二、判法（有界、可复核）
```
① 只看 6 类文件：scripts/check_*.py · scripts/audit_*.py · scripts/gen_*.py · tools/*.py
② 取它们**模块级**的 def（含 `_` 开头的私有函数）
③ 排除入口点：main / register / run
④ 数该名字**在整个仓库**（scripts · mcp-server · tools · tests · subskills）里
   除定义行与注释外还出现几次 ⇒ **0 次**即可疑
```

## 三、★ 结果：**164 扫过 · 1 可疑 · 1 真**（假阳性 **0%**）
| 可疑 | 判定 |
|---|---|
| `tools/propose_capability_sources.py:133` `match_modules(kws, files)` | ✗ **真的死代码** —— 它是 `stems_only()` 的**旧版**：会**扫文件体**（`body = f.read_text(...)[:1200]`），而 `stems_only()` 的 docstring 明写「**只按文件名主干**匹配（**不再扫文件体**）」「⚠ 第一版还扫了文件体 ⇒ 命中面进一步失控」 |

⇒ ★★ **被取代的旧版，作者留了说明却没删函数** —— 于是它作为死代码留在仓库里。

### 处置
* **删掉它**，并在原处留一条**墓碑注释**（写明它是谁、为什么删）——
  ⚠ 留注释而不是无声删掉：**读代码的人该知道这里发生过什么**；
* 删除是**可 git 追溯**的（提交信息里写了依据）。

## 四、★ 假阳性 0% —— 但**样本只有 n=1**
```
164 扫过 · 1 可疑 · 1 真 ⇒ 表面假阳性率 0%
⚠★ 但 n=1 **不足以**说"这个探针可靠" —— 一个数据点估不出率
⇒ ★ **不把它升成硬门禁**（那会挡住发布）；**先做成回归测试**，
  并对"动态调用"类留**显式豁免表**（`UNCALLED_EXEMPT`，每条带理由）。
⇒ 将来样本多了再考虑接进 `release_check`。
```
★ 这与本项目此前几次**方向相反**（`052`/`054` 都是"假阳性太高 ⇒ 不成门禁"）；
本轮是"**假阳性低，但样本太少 ⇒ 先不进硬门禁**" —— **两种克制是同一种**。

## 五、★ 一条**方法**上的自我纠正
```
第一版测试：它**自己重写了一遍判法**（`_fake_suspects`）来跑负例
⇒ ★ 那不叫"测到了工具" —— 测的是"测试自己写的一份"（事实 62 的精神）
⇒ 改成：把判法抽成 `probe.find_uncalled(root=…)`，
  **`main()` 与测试跑同一份代码**
```
⚠ 这条值得记：**负例如果绕开被测对象，就只是"另一个实现的自测"。**

## 六、与其它记录的关系
```
事实 40  存在但没人用的守卫 ≡ 没有守卫          ←  本条的**类**（常量形态在 053/054）
事实 61  好用的工具函数要用在所有同类场合        ←  本条的**动机**（定则④）
事实 62  门禁"写了"≠"有效"，负例是唯一的证明     ←  本条的**方法**（且本轮还纠正了负例的写法）
事实 74  按名字判语义的检查做不成门禁            ←  本条的**边界**（本探针判的是**结构**，不是语义）
```
★ 合起来：**判"结构"（有没有被调用）比判"语义"（是不是长度）可靠得多。**

```

⇒ ★ 结构类**没有"解释空间"**：一个文件要么在清单里、要么不在。
```
★ 而这一点在本轮被**再推进一步**：

### ★★ 结构类判据**可以被"故障注入"确定性地验证**（事实 62）
```
① 基线              : exit=0 · 5 passed
② **造故障**（往 mcp-server/ 放一个没登记的 tool_specs_batch99.py）
                    : exit=1 · **1 failed** ⇒ 判据确实会红
③ 复原（删掉假文件） : exit=0 · 5 passed
```
⚠ **这一点名称/语义类判据做不到** ——
你想"注入一个假故障"时，**先得说清"什么叫错"**，而那正是它判不了的东西。
⇒ ★★ **"能不能被故障注入验证"本身就是一条分界线：**
**能注入的是结构判据，不能注入的是语义判据。**

## 一、判法（**纯集合比对**）
```
server.py 的 45 条  ∪  batch 模块的 41 条  ==  协议层实际给出的 86 条？
```
⚠ **安全**：起 server **只发 `initialize` + `tools/list`**，**一次工具都不调** ⇒ **不碰 COM**
（事实 24）。

## 二、★ 结果：**45 + 41 = 86 ✓ 完全对上**
| 方向 | 结果 |
|---|---|
| `server.py` 声明了、**却没进协议层** | **0** |
| 协议层有、`server.py` 里找不到声明 | **41** —— ★ **正好是 `register_capabilities` 贡献的那 41 条**（第二条注册路径）|
| **两条路径之间重名** | **0** |
| 每条路径**内部**重名 | **0** |

## 三、★★ 本轮查出的第一件事：**跨路径重名此前无人检查**
```
`tool_registry.check_specs` 只查 **batch 路径内部**的重名
⇒ ★ **两条注册路径之间的重名没有任何检查** ——
  若有人把同一名字加到 server.py 与某个 batch，**没人会拦**，
  而那时"哪一个赢"取决于注册顺序 ⇒ **不确定**。
⇒ ★ 而且从**协议层看不出来**（`tools/list` 是集合，重名会被去重）
⇒ 必须在**声明层**拦。已补 4 条结构判据。
```

## 四、★★★ 本轮查出的第二件事：**一个"顺手套上 fixture"的动作，会让判据在故障时静默跳过**
```
第一版把 `test_no_tool_is_declared_in_both_paths` 写成收 `tools` fixture
⇒ 故障注入时它报了 **`1 skipped`**（不是 failed）
⇒ 原因：重名让**注册失败 ⇒ server 起不来** ⇒ `tools` fixture 拿不到响应就 `skip`
⇒ ★★ **判据"恰好在被测故障发生时静默跳过"** —— 那是**最坏**的失效方式
   （比"没写这条判据"更糟：它看着是绿的）
⇒ 修法：这条判据**只看两个声明来源**（源码 + `all_specs()`），**不碰协议层**
```
★ 而这正与 `053`/`054` 那条呼应：**一条判据必须能被负例证伪** ——
"会 skip"等效于"不能被证伪"。

## 五、★ 一次**我自己的实验做错了**（如实记）
```
第一次故障注入：我往 batch10 塞了 `solidworks_current_selection`
⇒ 以为它"在 server.py 里"——**其实它在 batch 里**（协议层那 41 条之一）
⇒ 于是造出的是 **batch 内部重复**，而**跨路径**判据正确地保持绿
⇒ ⚠★ 而且我用 `-k declared_in_both` **只跑了一条**，把内部重复那条**排除了**
⇒ 结论：**是实验错了，不是判据错了** —— 换成真在 server.py 里的名字后，判据立刻红。
```
★ 教训：**故障注入本身也要"注对东西"** —— 否则会把"实验设计错"读成"判据失效"。
