# 外部评审稿写法（通用方法论）

> **适用**：你要把一件自己没把握的复杂事，交给一个不熟悉你项目的外部专家（或高级 AI），请对方给方案、做判断、挑毛病。
>
> **本文不针对任何具体项目**。所有原则都来自实际踩过的坑，每条都注明了「不这么做会怎样」。本文既供人阅读，也可作为 AI 执行的技能说明，AI 请先读「使用入口」。
>
> **一句话主张**：评审稿不是"把我的情况讲一遍"，而是"让对方能动手"。前者以信息完整为标准，后者以对方可执行为标准。
>
> **检验标准只有一条**：读完的人，能不能动手？

## 使用入口（先读这一节）

### 何时用，何时不用

- **用**：要把复杂、没把握、需要外部判断的事交给外部专家或另一个 AI；或要审查一份已有的评审稿。
- **不用**：同事之间的日常沟通；纯代码或纯文档的改写；指令已完全明确、无需判断的执行任务。

### 两种模式

| 维度 | 模式 A · 起草（Generator） | 模式 B · 对抗审查（Auditor） |
|---|---|---|
| 做什么 | 把散乱资料拼装成一份符合规范的评审稿 | 对已有稿子扮演刁钻外部专家，逐条找茬 |
| 依据 | 施工流程（Phase 1–5）、十节骨架、十一条硬规则 | 十一条硬规则、第 7 部分自查清单、第 5 部分多路评审 |
| 产出 | 评审稿；待对方澄清的事项写进节 6 | 缺陷清单：类别 ／ 位置 ／ 为什么是硬伤 ／ 具体改法 |
| 能否改稿 | 能，它本来就是在写稿 | 不改稿，只报告（见 5.2） |

**推荐顺序：先 A 起草，再 B 自审。** B 最好在新会话中进行，避免沿用起草时的思路。真实案例中，一份已自查三轮的稿子，仍被审出 30 处读者会卡住的地方。

### 调用方式

指令 A（起草）：

```text
请根据 external-review-brief-guide.md 的"施工流程"（Phase 1–5），
把以下材料整理成一份符合规范的外部评审稿。

先检查"开工前：输入门槛"的四项是否齐备。缺哪一项，先问我，不要编造；
只有我确认某项确实不存在时，才写"此项目前没有"。

材料：<你的散乱资料>
```

指令 B（自审）：

```text
请根据 external-review-brief-guide.md 的十一条硬规则与第 7 部分自查清单，
扮演一个外部刁钻专家，对下面这份评审稿做对抗性审查。

只找三类硬伤：
① 看不懂：黑话、未定义术语、抽象示例
② 答不了：缺数据、约束死锁、无边界的问题
③ 没法用：不知道交什么、什么算合格、协作边界不明

逐条给出：原文位置（节标题 + 段落）＋ 为什么是硬伤 ＋ 具体改法。
只报告，不修改稿子。不要客套，不要"总的来说写得不错"。

待审稿：<你的稿子>
```

### 开工前：输入门槛

起草前，四项输入必须齐备。缺哪一项，稿子就会在对应的地方失效。

| # | 输入 | 说明 | 缺了会怎样 |
|---|---|---|---|
| 1 | 现状事实集 | 代码行数、已有工具或功能数、已知缺陷数据（原始数字，不美化） | 读者无法判断规模，稿子变成空谈 |
| 2 | 约束边界 | 环境（单机、离线、并发）、硬件配置、团队人力、依赖政策 | 读者无法判断技术选型的可行域 |
| 3 | 待决策列表 | 架构分歧点、未决方案、拿不准的路线选择 | 读者不知道该回答什么 |
| 4 | 真实样本 | 底层核心对象的 1–2 个真实代码或数据片段 | 读者设计不出接口 |

缺项怎么办，取决于谁在执行：

- **AI 正在与用户对话**：先一次性列出所有缺项，问用户。只有用户确认某项确实不存在时，才在稿子里写「此项目前没有」，并注明「这正是需要对方设计的部分」。真实案例中，作者写「我们目前没有历史任务语料库」，反而让读者给出了「先构造语料」的方法，而不是放弃回答。
- **对方只能一次性阅读、不能追问**：同样写「此项目前没有」，不编造。

无论哪种情况，都不编数字：只用原始数据或实测值；没有实测值的，写「未测」，并列入节 6。没定的政策也不替用户定，写成明确的二选一，留给用户或对方选。

### 施工流程（模式 A）

| 阶段 | 动作 | 通过判据 | 详见 |
|---|---|---|---|
| Phase 1 · 套骨架 | 套用十节骨架；前三行锁定"这是什么 ／ 现状一句话 ／ 要什么" | 只读前三行，能说出项目与诉求 | 1.1、1.3 |
| Phase 2 · 区分事实与假设 | 把结论降级为假设，补齐竞争解释；每个判断标注"事实"或"假设" | 没有未标注的判断 | 规则 4 |
| Phase 3 · 对抗自审 | 以刁钻外部专家的身份，专找约束冲突、无法实现的示例、无边界的问题；找到的问题全部修掉 | 至少找出 3 处问题，且已修复 | 规则 1、2、6；第 7 部分 |
| Phase 4 · 防嫁接与数字对账 | 替换示例后做实体词全局扫描（防嫁接：旧示例的内容残留在新稿里）；逐个复算数字 | 旧示例的实体词命中数为 0；每个数字有口径 | 5.6；规则 3 |
| Phase 5 · 终版装配 | 附分批交付指引、真实样本附录、协作边界 | 读者读完能动手 | 1.4、1.5、6.2 |

### 十一条硬规则（速查）

完整说明见第 2 部分。下表最后一列是交稿前可以逐条自问的问题。

| # | 规则 | 自检问题 |
|---|---|---|
| 1 | 例子在你的能力圈内 | 论证用的例子，底层工具或方案真的做得到吗？ |
| 2 | 约束之间不打架 | 通读所有约束，两两之间有冲突吗？ |
| 3 | 数字可复现 | 每个数字有口径吗？同源数字只定义了一次吗？你复算过吗？ |
| 4 | 事实与假设分开标 | 每个判断都标了"事实"或"假设"吗？竞争解释给了吗？ |
| 5 | 不问自己能答的问题 | 这个答案我自己能推出来吗？能，就删掉 |
| 6 | 问题不复合、不伪二分、有边界 | 一个编号只问一件事吗？给了篇幅与格式吗？ |
| 7 | 标篇幅，并给"只能答三问" | 每题标了期望篇幅吗？有问题总览和优先级吗？ |
| 8 | 给"答不了"的出口 | 有没有可能无解的问题，却没有明说？ |
| 9 | 判据四段式，含反向验证 | 每条判据都有检查方式、通过条件和反向验证吗？ |
| 10 | 运行时拓扑写明 | 谁调谁、谁驱动主循环、受什么限制，写清楚了吗？ |
| 11 | 定量问题先给基准数据 | 要阈值、选型或预算的问题，题干里有实测基准吗？ |

### 完成标准

交稿前，以下五项全部满足（或写明未做的项及原因）：

1. 第 7 部分自查清单逐条通过
2. 附录 B 的脚本自测通过，并对稿子扫描无报错
3. 若换过示例：旧示例的实体词命中数为 0
4. 版本已冻结，并记录了哈希值（见 5.4）
5. 模式 B 已跑过一轮，每条发现都回到原始数据核过后才改

## 第 0 部分 · 先明确三件事

### 0.1 外部专家的处境（这决定一切）

写稿之前，先站在对方的位置想清楚：

| 对方的处境 | 后果 |
|---|---|
| 读不到你的任何文件 | 你写的就是全部输入，漏了就是没有 |
| 不能追问，或追问很贵 | 问题必须一次问清 |
| 不懂你的内部术语 | 你的黑话对他等于乱码 |
| 不知道自己的角色 | 他不知道该给决策建议，还是给可直接落地的方案 |
| 有输出长度上限 | 你要求一次交完，他只能压缩成空话 |
| 看不到你的代码和数据 | 你让他设计接口，他连现有接口长什么样都不知道 |

> **核心判断**：你的稿子不是写给自己看的"情况说明"，而是给对方用的"作业指导书"。

"不能追问"只在对方真的无法交互时成立。若对方可以随时追问，"一次问清"的压力可以放宽，其余规则照常适用。

### 0.2 三种失败模式

真实案例中，同一份稿子连续被指出三类失败：

| 失败模式 | 表现 | 后果 |
|---|---|---|
| 看不懂 | 术语没定义，例子太抽象，内部黑话 | 读者理解错，方案建立在错误前提上 |
| 答不了 | 缺关键数据，约束自相矛盾，问题无边界 | 读者只能泛泛而谈，或退回一堆反问 |
| 没法用 | 不知道要交什么，什么算合格，能不能读代码 | 读者交出的东西，作者接不上 |

三类要分别检查。修好一类，不代表另两类没问题。

### 0.3 先当一次读者

写完初稿后，假装自己就是那个外部专家，从头读一遍。每到一处"我缺信息，没法判断"，就记下来。

这一步成本最低，却最容易被跳过：作者对自己的稿子太熟，会不自觉地补全缺口。

> 真实案例：一位扮演"读者代言人"的评审者逐条列出了 30 处他会卡住的地方，结论是"我读完交不出你要的方案"。而那份稿子此前已被作者自查过 3 轮。

## 第 1 部分 · 结构：一份能用的评审稿长什么样

### 1.1 推荐骨架（十节）

下面骨架中的"节 0–节 9"指评审稿自己的章节。本指南自身的章节用"第 N 部分"和"N.N"表示，两者不要混用。

```text
节 0  名词定义          ← 必须最前，定义先于使用
节 1  摘要              ← 只读这一节也能明白全貌
节 2  目标              ← 要做什么，+ 明确不做哪些（Anti-Scope，即不做的范围）
节 3  现状              ← 手里有什么、做到哪了
                          ★ 必须内嵌运行时拓扑：谁调谁、主循环谁控制（见规则 10）
节 4  核心发现 / 问题    ← 你发现的关键事实，带证据
节 5  根因 / 你的判断    ← 明确标为"假设"，并给竞争解释
节 6  待决策的分歧点     ← 你拿不准的路线选择
节 7  请对方回答的问题   ← 编号、分组、标篇幅、给优先级
节 8  交付要求          ← 交什么、什么格式、什么算合格，+ 协作边界
节 9  约束条件          ← 环境、资源、红线，+ 你自己的资源（供对方排序）
附录 A/B/C              ← 证据明细 ／ 术语表 ／ 真实样本（让对方能设计接口）
结尾                    ← 下一步，+ 分批交付指引
```

两个最容易漏的锚点：

| 锚点 | 为什么容易漏 | 漏了会怎样 |
|---|---|---|
| 节 2 的 Anti-Scope | 起草时只想到"要做什么" | 例子跑到能力圈外（规则 1）。真实事故：用做不到的产品当主示例 |
| 节 3 的运行时拓扑 | 起草时只堆代码行数、工具数量 | 读者按猜的调用机制设计接口（规则 10）。真实事故：读者困惑"你到底怎么跑起来的" |

### 1.2 名词定义必须放最前

这是最容易犯、代价最大的错误。

真实案例：一份稿子把术语定义放在第 75 行，而摘要在定义出现之前就用了核心词 24 次：

> "方法层只有 4 个方法，还没接通"——读者不知道"方法"是什么。

规则：

- 定义必须出现在第一次使用之前
- 每个词只有一个意思，全文不换义
- 一个词有多重含义时（真实案例中，"能力"一词被当成 5 种意思用），改词，不要加提醒

### 1.3 摘要要能独立成立

标准：只读摘要的人，应该能说出"这是什么项目、现状如何、要我做什么"。

真实教训：一份稿子的摘要在定义之前就用了未定义的词；另一份稿子的第一屏全是免责声明和元信息，真正的"这是什么项目"要到第 134 行才出现。

改法：标题下前三行就说清：

```text
这是什么项目：<一句话>
现状一句话：<关键数字对比>
我们要什么：<你要交什么>
```

### 1.4 附录要放真实样本，不是描述

这是让方案能落地的关键。

真实案例：一位评审者说，交付要求中的"每阶段目标"和"每阶段验收方法"，全部依赖他看不到的资产（工具名、数据结构、检查清单），他"能写出的只有架构层方向"。他点名需要五样东西：现有定义的真实样本、字段清单、命名样本、检查清单、原始规划全文。补上之后，他的结论从"交不出"变成了"可以动手"。

规则：凡是你要对方设计接口或扩展的东西，给一个真实样本（脱敏可以，但结构要真实）。

| 你要他做什么 | 你必须给什么 |
|---|---|
| 设计 A 与 B 之间的接口 | A 与 B 各一个真实样本 |
| 扩展某套规则 | 现有规则的一条完整原文 |
| 接入现有检查机制 | 检查清单（哪怕只列名字） |
| 判断某决策是否可行 | 相关的硬约束数据（如硬件规格） |

### 1.5 结尾要给"下一步"与"分批指引"

真实教训：一份稿子的文档最后一行是术语表，收在一个定义上，泄气。

更要紧的是输出长度上限。如果要求对方一次交完一份上万字的方案，他要么被截断，要么为了不被截断而大幅压缩细节，退化成高谈阔论。所以结尾要给分批方案：

| 批次 | 内容 |
|---|---|
| 第一批 | 核心架构，加最关键的三问 |
| 第二批 | 其余问题 |
| 第三批 | 详细施工方案，加验收判据 |

## 第 2 部分 · 内容：十一条硬规则

### 规则 1 · 例子必须在你的能力圈内

真实事故：一份稿子用"给我建模一个鼠标"当主示例，论证需要任务拆解层。但项目自己的约束写着"曲面工具能力受限"，而鼠标外壳恰恰是自由曲面。

后果：论据在可行性上本身站不住。读者分不清，是拆解层设计错了，还是底层工具没有这个能力。懂行的读者会立刻质疑：连基础特征都没走稳，核心示例为什么盯着做不到的东西？

规则：用能力圈内的例子。某类需求明确不做的，明说不做，并写出理由（写进节 2 的 Anti-Scope）。

### 规则 2 · 约束之间不能打架

真实事故 A：一处写"核心功能不能依赖外网"，另一处又给"本地模型 vs 云端 API"二选一。读者若严格遵守前者，就只能选本地；但看到后者，又发现作者其实倾向云端。他的方案前提建立在流沙上。

真实事故 B：稿子排除了"不要继续加方法"这条路线，却在问题里问"做不成后退回什么？（若答案是退回加方法，请说明为什么那条路仍然可行）"。这等于"我们已经枪毙了方案 A，但若你的 Plan B 要用 A，请向我们证明我们错了"。读者会被迫花大量篇幅辩护，而不是聚焦技术。

规则：

- 写完后通读全部约束，检查两两之间是否冲突
- 排除某条路线时，写"若你认为我们排除错了，请直接反驳"，不要写"请证明我们错了"
- 某条政策你没定，给明确的二选一，不要让读者替你定

### 规则 3 · 数字必须可复现

真实事故：稿子写"476 行数据全覆盖"。核查后发现，476 行里只有 198 行有结论，278 行是"未知"，有结论的只占 41.6%。读者据此排的施工阶段前提不成立：他以为"数据都在，只差接线"，实际是一半数据还没有。

同类问题：

- 同一件事有两个数（35 与 36；4 个模块与 6 个模块）
- 数字没有口径（"87,000 行"含不含注释？）
- 不同来源同名不同义（"工具合计 521"与"本仓 476"）

规则：

- 每个数字写明口径：怎么数的，含什么、不含什么
- 同源数字只在一处定义，别处引用
- 自查时逐个复算。真实案例中，一份稿子被审出 11 处数字错误，其中 1 处会直接污染方案骨架

#### 进阶：多个事实来源，用对账表

真实案例：同一个属性（"某操作会不会改数据"）在系统里有三个来源：人工标记 35，静态推断再加 36，运行时策略合计 71（前两者合并，并对未知项保守处理）。作者初稿只给了 36，读者发现对不上，怀疑还有第三个隐藏的规则文件。

正确做法是给对账表，不要抹平成一个假数字，也不要只扔一个总数：

| 要素 | 说明 |
|---|---|
| 来源清单 | 每个来源的名字、覆盖范围、性质 |
| 交集与并集 | A∩B 多少，A∪B 多少，差额从哪来 |
| 裁决优先级 | 冲突时以谁为准，为什么 |
| 未知项 | 有多少是判不出的（未知 ≠ 否） |

核心原则：向外部专家暴露真实的不一致，比给一个看似完美、经不起推敲的数字更有价值。真实案例中，作者把三个数的关系理清后，评审评价为"彻底咬合"。

### 规则 4 · 事实与假设要分开标

真实事故：稿子把"根因是缺某一层"写成了结论，而它其实是假设。同样的数据下，至少有三个竞争解释。读者按这个"结论"出方案，等于在未验证的诊断上盖楼。

规则：

- 明确标出哪些是事实、哪些是待验证的假设
- 给出竞争解释，哪怕你倾向其中一个
- 主动写："若你认为根因在别处，请直接说。那比顺着我们的框架答更有价值。"

这句话把读者的角色从执行者变成了裁判，是全文姿态最好的句子之一。

### 规则 5 · 别问自己就能答的问题

真实事故：13 个问题里，评审判定有 5 个不该按原样问：

| 类型 | 例子 | 为什么不该问 |
|---|---|---|
| 答案已在稿子里 | "方法与工具是分层还是平铺？" | 稿子已给出依据，再问等于让读者重走已被否决的选项 |
| 会引向已排除的路 | "先扩数量还是先打通？" | 稿子已论证前者是错方向，再问等于让读者确认已知结论 |
| 取决于你方资源 | "先做哪个？" | 顺序取决于你的资源与风险承受力，读者没有这些信息 |

规则：每个问题问之前，先自问一句："这个答案我自己能不能推出来？"能推出来的别问；推不出来的，问。

### 规则 6 · 问题不能复合、伪二分或无边界

真实事故 A：一个编号下塞了 4 个子问题，读者必然只答 1–2 个。

真实事故 B：三个问题都是伪二分（"分层还是平铺"、"扩数量还是打通"、"独立还是并入"），而正解可能是第三种，例如"内部执行分层、对外只暴露工具"。

| 毛病 | 改法 |
|---|---|
| 复合句 | 拆成独立编号，一个编号只问一件事 |
| 伪二分 | 改成开放式，但给约束："请给出你的方案，并说明为什么不是另外两种" |
| 问题太大 | 给判定对象："请回答 (a)…(b)…(c)…" |
| 开放式无边界 | 给篇幅与格式，如"可用表格，不限篇幅" |

### 规则 7 · 标篇幅，并给"只能答三问"的清单

真实事故：13 个问题里，一题的体量约为另两题的 4 倍。读者会把力气全压在那一题，其余各用一句话敷衍。

规则：

- 每题标期望篇幅（约 200 字、约 300 字，或不限）
- 开头给问题总览表：编号、分组、一句话、篇幅
- 明确写出优先级，例如："如果只能答三问，请答 Q2、Q3、Q9。"

### 规则 8 · 给"答不了"的出口

真实事故：有个问题涉及业内未解的难题（语义正确性的自动判定）。稿子要求"给确定性算法"，读者只能编一个假的。

规则：凡是你自己觉得可能无解的问题，明说"这可能无解"。否则读者会为了交差而编造。

两类特殊问题，有标准的提问姿态：

类型 A · 涉及人机交互或中断。不同运行形态下答案完全不同。先写明默认运行环境的限制（例如"本协议没有原生的悬停确认机制"），再问：

> 在此约束下，你主张如何折中？若必须实现人机确认，系统应在哪个边界拦截？

类型 B · 涉及业内未解难题或语义判断。确定性的规则做不到，硬要求会逼读者编。主动承认规则无法判定，然后给三条路，让对方评判：

| 路 | 做法 | 要对方回答的问题 |
|---|---|---|
| A 路 | 让大模型打分（LLM-as-a-Judge，即让大模型当裁判） | 承认有随机性，这算不算合格的机器判据？ |
| B 路 | 人工标注黄金集 | 成本与规模的边界在哪？谁来标，需要领域专家吗？ |
| C 路 | 下游执行反向暴露：让真实执行时的失败，反推上游的错误 | 这条路够不够？ |

真实案例中，作者写"我们知道这是一个业内未解问题——不要强行给确定性算法"，被评审评为全文姿态最好的句子之一。它向专家证明提问者懂行，别想用套话糊弄。

### 规则 9 · 判据要可机器判定，并给四段式

判据：一条可以判真假的验收条件。

真实事故：稿子要求"验收方法要可机器判定"，但只给了中文句子形式的例子，读起来像 KPI，不像可以运行的检查。

规则：判据写成四段：

```text
① 判据        一句话，可判真假
② 检查方式    怎么测：读什么、跑什么、比什么
③ 通过条件    具体的数或布尔条件
④ 反向验证    怎么证明"把修复去掉，它会失败"
```

第 ④ 段是关键。没有它，一条检查可能永远通过，成为废检查。

术语警告：真实案例中，稿子把这个概念叫"红基线"，读者极易理解成"已知失败的红线、告警阈值"，从而交出格式对、内容全错的方案。改成大白话"反向验证"，并就地解释。

### 规则 10 · 运行时拓扑要写明：谁调谁，谁驱动主循环

运行时拓扑：运行时各角色之间，谁调用谁、谁驱动主循环。Agent：会自己调用工具、按步骤完成任务的 AI 角色。

真实事故：稿子频繁提到"Agent / 工具 / 服务"等角色，却通篇没有运行时拓扑图。第 3 轮评审时，评审者强烈困惑：

> 你们到底是一个 Python 脚本自己调自己，还是外部客户端连进来？这决定我给的接口设计，但稿子里看不出来。

后果：没有拓扑，外部专家给出的接口设计几乎一定会与实际调用机制错位。

必须交代三件事：

| 角色 | 要回答的问题 |
|---|---|
| ① Agent 跑在哪一侧 | 外部客户端连进来（你是被动提供方），还是你自己的主循环（你是主动方）？ |
| ② 主编排循环谁控制 | 有没有总控？它决定顺序、重试、状态吗？ |
| ③ 执行环境的限制 | 并发限制？单实例？进程模型？有没有会死锁的东西？ |

参照示例（真实案例的拓扑）：

```text
当前实际在用（形态 B · 被动提供方）：
  外部客户端 →[协议]→ 你的服务 →[底层 API]→ 受控应用
  ↑ Agent 跑在客户端侧          ↑ 单实例，多进程会死锁

已实现但未启用（形态 A · 主动编排）：
  自带编排器 →[CLI]→ 外部 Agent CLI → 回到服务层
  ↑ 能做阶段规划、重试、评审门      ↑ 尚未接通
```

并且要说明"当前实际在用哪一条"。否则读者会按他猜的那条设计。

### 规则 11 · 定量问题前，先给基准数据

真实事故（两处，同一个根因）：

| 原问题 | 为什么答不了 | 应先补的基准 |
|---|---|---|
| "上下文预算定多少合适？" | 读者不知道你现有多少内容，无法估算 | 实测：现有定义合计约 22 万字符，粗估 10–15 万 token |
| "本地模型的质量上限够不够？" | 读者不知道显存 | 实测：RTX 4080 SUPER，16 GB 显存 |

规则：凡是要求对方给阈值、做选型、定预算的问题，题干里必须内嵌实测的基准数据。绝不能让对方在真空中盲猜工程参数。

先给基准的对照表：

| 你要对方给什么 | 你必须先提供 |
|---|---|
| 阈值或预算 | 当前的实际量级（实测值） |
| 技术选型 | 硬件规格，以及依赖政策（能不能联网、能不能引库） |
| 工作量估计 | 团队规模，以及单次操作的成本 |
| 覆盖目标 | 现有覆盖率的分子与分母 |
| 性能目标 | 当前的实测基线 |

一句话：没有基准的定量问题，等于让读者编数字。

## 第 3 部分 · 语言：把黑话翻译掉

### 3.1 三类词，三种处理

真实案例中，一份稿子被审出 75 个外部读者看不懂的词。

| 类别 | 例子 | 处理 |
|---|---|---|
| 内部黑话 | 台账、门禁、真机、回读、效应表、收口、探针 | 换成大白话，或首次出现时就地加括号解释 |
| 专业术语 | 抽壳、放样、回转体、标准件、尺寸链、自由度 | 不要删（那是内容），加一句解释 |
| 自造词 | 拆解层、叶子任务、任务域 | 定义清楚，并说明它与已有概念的关系 |

### 3.2 检查方法

逐词扫描：把稿子里所有名词列出来，对每个词问：

1. 一个不懂这个项目的人，看到这个词会想到什么？
2. 我第一次用它之前，解释过吗？
3. 它在全文里是否只有一个意思？

特别检查：读者要在交付物中产出的那些词。如果他理解错了，会交出格式对、内容全错的方案。

真实案例：稿子要求读者给"红基线构造"，而这个词在附录里才解释。读者读到要求时，早已形成错误理解。

### 3.3 改词，不加提醒

提醒读者"注意"，是把负担推给读者，读者得记住"这里要小心"。正确做法是换掉造成混淆的词，读者就不需要额外工作。

| 反模式 | 正模式 |
|---|---|
| 加一节"容易混淆的词" | 换掉那个词 |
| "注意：这里的 A 不是 B" | 把 A 改名成不会与 B 混淆的词 |
| "本文档的 X 与 Y 不同" | 统一成一个词，或各起一个准确的名字 |

## 第 4 部分 · 视觉：别让形式毁掉内容

真实案例中，一份内容质量很高的稿子，被审出 8 类视觉问题：

| 问题 | 实测 | 后果 |
|---|---|---|
| 框线错位 | ASCII 图的右边框与内容差 2–8 列 | 读者看到的第一张图就"散架"，立刻传递"没人校过"的信号 |
| 加粗通胀 | 659 处加粗，40% 的行含加粗 | 到处加粗，就等于没有加粗 |
| 表格伪装 | 45 个表里有 21 个只有 2–3 行，15 个是伪装成表格的定义清单 | 单维度内容用列表更快，多维度对比才值得用表格 |
| 重复表 | 附录与正文有 5–6 处整表重复 | 浪费读者时间，且两处可能不一致 |
| 空表头 | `\| \| \|` 渲染出无列名的表 | 显得没有校对 |
| 缺分隔线 | 表头下少一行 `\|---\|---\|` | 整张表塌陷成混着管道符的纯文本 |
| 符号一符多义 | 同一符号同时当"优先级""更正标记""图内解说" | 读者无法从符号推断重要性 |
| 符号形态混用 | 同一符号的两种 Unicode 形态并存 | 跨平台渲染的宽度和颜色都不同 |

规则：

- 多字节字符（中文等）不能用字符数补空格对齐，改用表格或列表
- 加粗只用于关键结论，不用于每个术语
- 同一件事只讲一次，别处用指针（"见 X 节"）
- 符号要么统一语义，要么不用。本指南的符号约定：★ 核心要点，⚠ 踩过的坑，✅ ／ ❌ 表示能 ／ 不能
- 表格必须有分隔线

真实事故：作者在改稿时插入一段引用块，把一张表格从中间劈开。表格后半截失去了表头与分隔线，塌陷成纯文本。作者通读两遍都没有发现，因为内容读起来是对的。人的注意力在语义上，不在语法上。视觉缺陷只有机器扫描才靠得住，见附录 B。

机械检查覆盖不到的，需要人工核对：框线对齐（中文按 2 列计）、语义正确性。

## 第 5 部分 · 过程：怎么把稿子改对

### 5.1 多路独立评审，各带一个视角

单一视角审不全。真实案例用了 5 路评审，每路只审一个角度：

| 视角 | 审什么 |
|---|---|
| 完整性 | 漏问了什么？尤其是"怎么算做完、做不成怎么办、拿什么数据判" |
| 清晰度 | 每个问题有没有歧义，能不能一次答清？ |
| 该不该问 | 哪些问题自己就能答？哪些会引向已排除的路？ |
| 对抗审查 | 找事实错误、因果漏洞、未验证的假设、自我美化 |
| 交付管理 | 站在乙方立场：读完能否直接开工？会反问什么？ |

如果只请一位，请对抗审查那一路。它抓出的事实错误最多（真实案例中为 11 处）。

执行方式：若环境支持子代理，各视角可并行开独立上下文；否则每一路单独开新会话，串行进行。自审也要换新会话，避免起草时的思路让自己看不见缺口。

### 5.2 评审者只读

要求评审者不得修改文件，只报告。理由：如果评审者顺手改了，你就分不清这是他的意见还是他的实现，多路评审之间也会互相覆盖。

### 5.3 收到意见：先核，再改

真实案例：对抗审查提出 11 条，作者逐条实跑核实，全部成立，包括一条"文档把某个数据说成全覆盖，实际只有 41.6%"。

但评审者也会错：真实案例中，一条"引用断链"的指控，核对后发现是评审者读的版本较旧。

规则：

- 每条意见都回到原始数据核一遍，不因为"他说得有道理"就改
- 核完再改，并在文档里记录改了什么

### 5.4 版本要冻结

真实事故：评审期间作者持续编辑文件（1116 行 → 1153 行），多位评审者审的是不同版本，行号全部对不上。

规则：

- 发出评审前冻结版本，记录哈希值（SHA256）。PowerShell 中可用 `Get-FileHash -Algorithm SHA256 <稿子路径>`
- 评审期间不改。要改，就等这一轮结束
- 必须改时，告诉评审者按"节标题"定位，不要用行号

### 5.5 反复迭代，直到没有结构性问题

真实案例的轮次：

| 轮 | 评审者 | 抓到的问题 |
|---|---|---|
| 1 | 5 路（见 5.1） | 漏问 8 题；7 题需改写；11 处事实错误 |
| 2 | 5 路 | 75 个黑话；30 处读者会卡住；结论"交不出方案" |
| 3 | 1 位外部专家 | 主示例与能力矛盾；约束死锁；缺运行时拓扑 |
| 4 | 1 位外部专家 | 文本嫁接事故（见 5.6）；概念定性错；约束仍冲突 |
| 5 | 1 位外部专家 | 定义摇摆；缺"阶段 0"声明；输出长度上限 |

每一轮都发现了新东西，而且后几轮的问题更根本：从文字层面，深入到前提层面。

### 5.6 换例子不等于换词：防嫁接

真实事故：作者用字符串替换，把主示例从 A 换成 B，但只改了标题，表格内部仍是 A 的全套内容。读者读到"用 B 走一遍"，表格里却全是 A 的零件名，再往下又突然跳回 B，会直接怀疑作者思维混乱。

根因：字符串替换只知道"标题里有 A 这个词"，不知道这个示例在新语境下还成不成立。

规则：

- 换例子，要把该示例的所有内容重新写一遍
- 改完通读整段，不要只 grep 那个词
- 特别检查：表格内部、代码块内部、附录副本

#### 实体词全局扫描协议

实体词：某个示例或概念特有的名词，如零件名、参数名、专有名词。靠肉眼通读会选择性忽略（真实案例中，作者自认为改完了，正文表格里其实还留着旧示例的全套零件名），所以要机械化：

1. 列出旧示例的实体词清单
2. 对全文做大小写无关的检索。附录 B 的脚本支持直接列出实体词；PowerShell 也可用 `Select-String`
3. 判据：命中数为 0，或仅出现在明确标注的更正声明里。不满足，就说明替换未完成，继续改

真实案例：旧示例为"鼠标"，实体词清单共 13 类：上壳、下壳、按键组、滚轮、电路板、蓝牙、USB、握持、握感、微动开关、电池仓、人体工学、手长。首次扫描 13 类全部命中（表格内部完全没改）；修正后命中数为 0。

这个协议不只用于换示例：

| 场景 | 实体词清单从哪来 |
|---|---|
| 换示例 | 旧示例的零件名、参数名、专有名词 |
| 改术语 | 旧术语的所有变体（缩写、英文、同义写法） |
| 换单位或口径 | 旧单位符号、旧口径名 |
| 删某个功能 | 该功能涉及的所有名词 |

## 第 6 部分 · 交付要求：写清"要什么，什么算合格"

### 6.1 四件套：每件交付物都要写清

| 项 | 要写清什么 | 不写清会怎样 |
|---|---|---|
| 要什么 | 交付物是什么；粒度如何（分几个阶段，每阶段多长） | 读者交出的东西粒度不对，无法接上 |
| 什么格式 | 建议的结构，并给模板 | 读者自由发挥，你无法比较不同方案 |
| 什么算合格 | 合格线，以及什么算不合格 | 读者按自己的标准交，很可能不是你要的 |
| 什么不想要 | 已试过并排除的方向（写法见 6.3） | 读者会重复提出你已经排除过的方案 |

真实教训：一份稿子只写了"要交什么"，没写"交到什么标准算合格"。读者会按自己的理解交，很可能不是作者要的。

### 6.2 协作边界（最容易漏，代价最大）

必须明说：

```text
你能读这份文档吗？          ✅
你能读我们的源码吗？        ❌
你能跑我们的测试吗？        ❌
你能访问我们的环境吗？      ❌
```

为什么重要：如果你要求"验收方法要可机器执行"，而读者不能跑代码，他就不知道该交"判据描述"，还是"可运行的测试"。

真实教训：一份稿子漏写了这段。评审者说：

> 文档让我"若需看源码请指出"，但本次被设定为不能追问、一次成型。结果：我若老实回答，交出的就是一份"我需要看这些"的清单。这两条要求互斥。

### 6.3 说清"不想要什么"，但语气要像"试过并排除"

"不想要什么"要说，但语气是"我们试过并排除了"，不是"我们不接受"：

| 反模式（像下单） | 正模式（像求助） |
|---|---|
| "我们不想要什么" | "我们试过并排除的方向" |
| "请勿复述" | "以下我们已知，若无新看法可跳过" |
| "不接受'建议分层'这类结论" | "'建议分层'这类结论对我们没用" |
| "若答案是退回 A，请说明为什么那条路仍然可行" | "若你认为我们排除错了，请直接反驳" |

真实教训：一位评审者说：

> 我是来帮忙的，不是来投标的。这几句会让我把原本想写的"你们可能忽略的第三个方向"删掉，只答你们问的问题。这对你们是损失。

### 6.4 说清自己的资源

读者要排阶段，需要知道你的资源：

| 项 | 为什么需要 |
|---|---|
| 团队规模 | 一个人能做完，和需要 5 人团队，方案完全不同 |
| 可用时间与硬期限 | 决定阶段划分的粗细 |
| 硬件 | 决定技术选型的可行域，比如本地模型能不能跑 |
| 依赖政策 | 能不能引入第三方库 |
| 产品形态与消费者 | 决定"成功"的定义 |

真实教训：一份稿子写了"有独立显卡（具体规格未测）"，读者被要求判断本地模型够不够用。他不知道显存，只能编。

规则：凡是要读者做判断的地方，先给他判断所需的数据（同规则 11）。

### 7.4 视觉

- [ ] 加粗只用于关键结论

### 7.5 交付

- [ ] 四件套齐：要什么 ／ 什么格式 ／ 什么算合格 ／ 什么不想要
- [ ] 协作边界已声明：能读什么，能跑什么
- [ ] 自身资源已给：团队、时间、硬件、政策
- [ ] 有分批交付指引

### 7.6 过程

- [ ] 多路独立评审，至少含一路对抗审查
- [ ] 评审者只读
- [ ] 每条意见都回到原始数据核过再改
- [ ] 版本已冻结，并记录了哈希值
- [ ] 换例子时通读了整段，并执行了实体词全局扫描（命中数为 0）
- [ ] 附录 B 的脚本已通过自测（见下）

> ★ 元规则：一个从未报过错的检查，不是好检查，而是可疑的检查。
>
> ⚠ 真实事故：一个检查表格分隔线的脚本，因多写了一个 `or not prev`，把"表头前是空行"这种最常见的排版当成"不是表头"而跳过，形成 100% 假阴性。它一直在运行、从不报错，看起来是绿的，实际什么都没有检查。
>
> 判据：必须能用合成负例证明"它有缺陷时会报"。

## 附录 B · 机械检查脚本

用途：检查评审稿的表格结构与代码围栏，并对换过的旧示例做实体词扫描。脚本只用标准库，需要 Python 3.7 及以上。

用法：

```text
python check_brief.py --selftest              先跑合成负例自测（每次扫描前都会自动跑）
python check_brief.py 稿子.md                 检查表格分隔线、空表头、列数、代码围栏配对
python check_brief.py 稿子.md 词1 词2         实体词扫描，命中即报出行号（判据：无报错）
```

脚本：

```python
import re, sys

CASES = [
    ("| a | b |\n|---|---|\n| 1 | 2 |", (), 0),
    ("| a | b |\n|:---|---:|\n| 1 | 2 |", (), 0),
    ("| a | b |\n| 1 | 2 |", (), 1),
    ("| | |\n|---|---|\n| x | y |", (), 1),
    ("| a | b |\n|---|---|\n| 1 | 2 | 3 |", (), 1),
    ("```\n| a | b |\n```", (), 0),
    ("```\n| a | b |", (), 1),
    ("| a | `x|y` |\n|---|---|\n| 1 | 2 |", (), 0),
    ("正文\n\n| a | b |\n| 1 | 2 |", (), 1),
    ("正文\n\n| a | b |\n|---|---|\n| 1 | 2 |", (), 0),
    ("正文提到 USB 接口", ("usb",), 1),
]

def cells(line):
    s = re.sub(r"`[^`]*`", "``", line.strip())
    return [c.strip() for c in s.strip("|").split("|")]

def is_row(s):
    s = s.strip()
    return len(s) > 1 and s.startswith("|") and s.endswith("|")

def is_sep(s):
    return is_row(s) and all(re.fullmatch(r":?-+:?", c) for c in cells(s))

def scan(text, ban=()):
    issues, block, in_code, fences = [], [], False, 0

    def flush():
        if block:
            n0, hdr = block[0]
            if all(c == "" for c in cells(hdr)):
                issues.append(f"L{n0} 空表头")
            if len(block) < 2 or not is_sep(block[1][1]):
                issues.append(f"L{n0} 表头下一行不是分隔线")
            width = len(cells(hdr))
            for n, row in block[1:]:
                if len(cells(row)) != width:
                    issues.append(f"L{n} 列数与表头 {width} 不一致")
            block.clear()

    for n, raw in enumerate(text.split("\n"), 1):
        s = raw.strip()
        if s.startswith("```"):
            fences += 1
            in_code = not in_code
            flush()
        elif not in_code and is_row(s):
            block.append((n, s))
        elif not in_code:
            flush()
        for t in ban:
            if t.lower() in raw.lower():
                issues.append(f"L{n} 命中实体词「{t}」")
    flush()
    if fences % 2:
        issues.append("代码围栏数量为奇数")
    return issues

def selftest():
    bad = [i for i, (t, b, e) in enumerate(CASES) if len(scan(t, b)) != e]
    print(f"selftest FAIL，失败用例序号：{bad}" if bad else f"selftest OK（{len(CASES)} 例）")
    return not bad

if __name__ == "__main__":
    sys.stdout.reconfigure(encoding="utf-8")
    if len(sys.argv) < 2:
        sys.exit("用法：python check_brief.py --selftest | 稿子.md [实体词...]")
    if not selftest():
        sys.exit(1)
    if sys.argv[1] == "--selftest":
        sys.exit(0)
    with open(sys.argv[1], encoding="utf-8") as f:
        issues = scan(f.read(), sys.argv[2:])
    print("\n".join(issues) if issues else "OK")
    sys.exit(1 if issues else 0)
```

不覆盖的检查（需人工）：框线对齐、加粗数量、语义正确性。

为什么脚本要自测：一个从未报过错的检查，可能根本没有在工作。所以脚本每次运行前，都先用合成负例自测，任一负例没报，就直接退出。
